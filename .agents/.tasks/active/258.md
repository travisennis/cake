# Guard destructive git stash operations in bash safety checks

## Summary

A delegated cake session ran `git stash 2>/dev/null` followed by `git stash pop` in the user's repository (observed 2026-07-12, session 98f4ccc8). The repo's git config was broken so both failed, but the pattern is a near-miss for data loss: if the stash-create silently saves nothing (clean tree or an error swallowed by `2>/dev/null`), the subsequent `git stash pop` consumes the user's pre-existing stash@{0}. This task adds `git stash pop` to the destructive-command guard and adds session-scoped stash tracking so a session can only pop/drop/clear stashes it created itself.

## Relevant Files

- `src/clients/tools/bash_safety/checks.rs` — add `git stash pop` detection to `check_git_stash`; add `StashTracker` logic
- `src/clients/tools/bash_safety/mod.rs` — update `CheckFn` signature or `validate_command_safety` to accept `&StashTracker`; register the updated check
- `src/clients/tools/bash.rs` — thread `StashTracker` from `ToolContext` into `validate_command_safety` at line 310
- `src/clients/tools/mod.rs` — `ToolContext` may need an optional `stash_tracker: Option<Arc<Mutex<StashTracker>>>` field (or similar) to persist stash state across bash tool calls within the same session

## Fix Direction

**Phase 1 — Block `git stash pop` unconditionally** (local, S-sized):
- In `check_git_stash`, add `git stash pop` to the existing `lower.contains(...)` guard alongside `drop` and `clear`.
- Update the error message to include `pop`.
- Update the test `allows_git_stash_other` to expect `pop` blocked instead of allowed.
- Update the chain test at line 898 (`git stash; git reset --hard; git stash pop`) — the pop in the chain may now be caught earlier, verify behavior.

**Phase 2 — Session-scoped stash tracking** (cross-module, drives S→M):
- Introduce a `StashTracker` struct (public in `bash_safety` or a new submodule) with a `session_created_stash: bool` flag and a `record_stash_creation()` / `may_access_stash() -> bool` API.
- Thread it through `validate_command_safety`. Options:
  a) Add `&StashTracker` parameter to `validate_command_safety` (breaking signature change).
  b) Use a `Cell<bool>` argument so the check can mutate tracking state as it scans commands.
  c) Store a shared `Arc<Mutex<StashTracker>>` in `ToolContext` so state persists across bash invocations in the same agent session.
- In `check_git_stash`: when a bare `git stash` or `git stash save`/`push` is seen, flip `session_created_stash = true`. When `pop`/`drop`/`clear` is seen, block unless `session_created_stash` is true.
- The tracker is reset when a new top-level session begins (new agent loop).

**Recommended approach**: Use option (c) — store `Option<Arc<Mutex<StashTracker>>>` in `ToolContext`. The agent loop creates a fresh `StashTracker` per session and passes it through tool context construction. This keeps `CheckFn` pure (it receives `&StashTracker` read-only via closure or parameter) while allowing cross-call state. The `PartialEq`/`Eq` derives on `ToolContext` will need attention (skip the tracker field in comparison, or wrap it).

## Acceptance Notes

- [ ] `git stash pop/drop/clear` are all blocked by the bash safety checks
- [ ] A session that never ran `git stash` (without pop/drop/clear) cannot silently pop, drop, or clear a stash in unattended mode
- [ ] A session that created a stash (via bare `git stash`, `git stash save`, or `git stash push`) can pop, drop, or clear it without friction
- [ ] `StashTracker` state is scoped to the session (reset on new agent loop)
- [ ] Existing tests are updated and new tests cover: block-pop, block-drop, block-clear, session-created-stash exemption, and the chain case (`git stash; git reset --hard; git stash pop`)
