# Cap provider Retry-After delays

## Summary

At commit `6e69b45`, parseable `Retry-After` values bypass the retry policy's 30-second maximum backoff. A provider or intermediary can therefore stall the CLI for an arbitrarily large delta or far-future HTTP date, while fallback exponential delays are bounded.

## Evidence

- `src/clients/retry.rs:12-31` — the default retry policy defines `max_backoff` as 30 seconds.
- `src/clients/retry.rs:295-301` — retry classification uses `parse_retry_after(headers).unwrap_or_else(fallback_delay)` directly.
- `src/clients/retry.rs:344-365` — both delta seconds and future HTTP dates become `Duration` values without clamping to policy limits.
- `src/clients/retry.rs:527-555` — parser tests verify ordinary values but do not cover a delay beyond the configured maximum.
- `docs/design-docs/api-retry-strategy.md:28-30` says `Retry-After` wins when parseable and describes fallback backoff as bounded; it does not define an unlimited server-controlled wait.

## Fix Direction

Apply an explicit upper bound to header-derived retry delays, preferably through the existing retry policy so custom policy tests remain deterministic. Preserve header precedence for reasonable values, HTTP-date parsing, retry classification, callback status, and retry budget. Update the retry design doc if the cap is a newly explicit behavioral contract. If providers require honoring longer delays for a known compatibility reason, stop and surface that decision rather than retaining an unbounded foreground stall.

## Acceptance Notes

- [ ] Large delta-second and far-future HTTP-date values are capped to the policy maximum.
- [ ] Ordinary `Retry-After` values below the cap are still honored exactly.
- [ ] Fallback backoff, jitter, retry counts, and no-retry headers remain unchanged.
- [ ] Retry status/progress reports the effective bounded delay.
- [ ] `cargo test retry` passes.
- [ ] `just ci` passes.
