# Repair recoverable invalid JSON in Edit tool arguments


## Problem

Analysis of 30 days of session transcripts (195 sessions, 1,084 Edit calls) shows an 11.7% Edit failure rate, and the single largest failure category (~60 calls, roughly half of all failures) is `Invalid edit arguments`: the model emitted malformed tool-call JSON and serde rejected the entire call before Edit preflight ran.

A significant fraction of these payloads are mechanically recoverable with lossless repairs:

- **Raw control characters inside JSON string literals** (18 observed: 14 literal tabs, 6 literal newlines — mostly while editing tab-indented Go files). JSON forbids raw control chars in strings, so escaping them in place (`\t`, `\n`, `\u00XX`) has no valid alternative interpretation. 15 of the 18 payloads parse cleanly after this single repair.
- **Trailing characters after a balanced top-level JSON object** (4 observed: doubled `}}` at the end, provider markup leakage after the object). Parsing the first complete JSON value and ignoring the remainder recovers these.

Together these repairs would have converted roughly a third of the invalid-JSON failures into successful calls. Failures that require guessing intent (quote desynchronization from escaping meltdowns) must NOT be repaired — they should still error.

## Relevant Files

- `src/clients/tools/edit.rs` — `parse_edit_args` is the entry point that rejects these payloads today.
- `src/clients/tools/write.rs` — Write parses the same style of large escaped-string arguments and has the same exposure; the repair layer should be shared, not Edit-only.
- `src/clients/tools/mod.rs` — candidate home for a shared argument-repair helper used by both tools.
- `src/clients/tools/edit_tests.rs` — existing Edit tests to extend.
- `docs/design-docs/tools.md` and `docs/guardrails/agent-loop-tools-and-tool-execution.md` — tool execution semantics docs to update (this changes what argument payloads are accepted, a tool-execution compatibility surface).

## Fix Direction

Add a conservative repair pass that runs only after strict `serde_json` parsing fails:

1. Scan the payload with a small state machine tracking in-string/escape state. Replace raw control characters (0x00–0x1F) found *inside string literals* with their JSON escape sequences. Do not touch anything outside strings.
2. If parsing still fails with a trailing-data error, parse the first complete top-level JSON value (e.g., `serde_json::StreamDeserializer`) and discard the remainder.
3. Re-run strict parsing on the repaired text. If it still fails, return the original error path unchanged — no speculative repairs of quoting/structure.

Repairs are deterministic and lossless by construction; if a repair produces the "wrong" string content, Edit preflight's exact-match validation still catches it with a recoverable no-match error.

Deliberately out of scope: repairing mismatched/desynchronized quotes, inferring missing fields, or any repair that requires choosing between interpretations.

## Acceptance Notes

- [ ] Raw tab and raw newline inside `old_text`/`new_text` string literals parse successfully and apply the intended edit.
- [ ] Trailing garbage after a balanced top-level object is ignored and the call succeeds.
- [ ] Quote-desync payloads still fail with the existing invalid-arguments error (no speculative repair).
- [ ] Repair layer is shared by Edit and Write argument parsing.
- [ ] Unit tests cover: control-char repair inside strings, control chars outside strings untouched, trailing-data recovery, unrepairable payloads still rejected, repaired-but-wrong content falling through to preflight no-match.
- [ ] Tool docs updated to describe lenient argument acceptance.
