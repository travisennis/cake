# Fix Chat Completions stream-json event ordering (message before function_call)

## Problem

In `src/clients/chat_completions.rs`, the `parse_choices` function emits `function_call` events **before** `message` events when a Chat Completions response contains both text content and tool calls. The order is:

```
[reasoning, function_call, message]  // current Chat Completions
```

But the Responses API backend (`src/clients/responses.rs`) correctly emits:

```
[reasoning, message, function_call]  // Responses API
```

This inconsistency means `stream-json` clients see different event ordering depending on which backend is used, and downstream consumers (like cake-repl) need workarounds.

## Root Cause

In `parse_choices` (lines 360-384 of `src/clients/chat_completions.rs`), tool calls are extracted first, then text content:

```rust
// Extract tool calls first      ← this emits FunctionCall before Message
if let Some(tool_calls) = &message.tool_calls { ... }

// Extract text content (may coexist with tool calls)
if let Some(content) = &message.content && !content.is_empty() { ... }
```

## Decision

Use the Responses API ordering as the canonical live and persisted conversation
order when an assistant turn contains both text and tool calls:

```
[reasoning, message, function_call]
```

This is an intentional event-order compatibility change for new Chat
Completions turns. Do not change the `ConversationItem`, `SessionRecord`, or
`StreamRecord` schemas, and do not migrate existing session files. Preserve
support for the historical `[reasoning, function_call, message]` order when
rebuilding Chat Completions request messages from older sessions.

## Scope of Fix

### 1. `src/clients/chat_completions.rs` — `parse_choices`

Swap the ordering of the "tool calls" and "text content" sections so text content comes first, matching the Responses API order.

### 2. `src/clients/chat_completions.rs` — `ChatMessageBuilder::push_function_call`

The current `ChatMessageBuilder` expects tool calls **before** their corresponding assistant message (forward merging: FunctionCall is accumulated as pending, then merged into the next Assistant message). After swapping `parse_choices`, the conversation history will contain `[Message(assistant), FunctionCall]` instead of `[FunctionCall, Message(assistant)]`.

The builder needs backward merging: when a `FunctionCall` item is pushed and the last message in `self.messages` is an assistant message with content but no `tool_calls`, retroactively add the tool call to that message. If the last message already has `tool_calls`, append to the existing list.

The existing forward-merge path in `push_message` (which checks `!self.pending_tool_calls.is_empty()`) should be preserved for backward compatibility with older session files that have the historical ordering.

### 3. `src/clients/chat_completions_tests.rs` — Update `parse_choices_tool_calls_with_text_content`

The test at line 1104 currently asserts tool calls come first:

```rust
// Tool call comes first
assert!(matches!(&items[0], ConversationItem::FunctionCall { .. }));
// Then the message
assert!(matches!(&items[1], ConversationItem::Message { ... }));
```

This needs to assert message comes first, tool calls second.

### 4. Builder tests — Verify both conversation orderings

Add or update builder coverage so the new `[Message(assistant), FunctionCall]`
order produces one assistant request message containing both `content` and
`tool_calls`. Cover multiple consecutive function calls after the message so
later calls append to the same assistant message.

Keep explicit coverage of the historical `[FunctionCall, Message(assistant)]`
order so older persisted sessions continue to produce the same request shape.
The existing `build_messages_assistant_text_with_tool_calls` snapshot currently
uses this historical order; either retain it and add new-order coverage or
rename/update it while adding a separate legacy-order regression test.

## Risks

- Low: only affects the Chat Completions backend path (Responses API unaffected)
- The `ChatMessageBuilder` change touches the `build_messages` path used for constructing all Chat Completions requests, but only alters behavior when a FunctionCall immediately follows an Assistant message with content
- Old session files with the historical `[FunctionCall, Message]` ordering are still handled correctly via the preserved forward-merge path
