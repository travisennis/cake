# Sandbox flag follow-ups: error-message hints, settings-dirs doc, policy foot-gun, test env hygiene

## Problem

Small follow-ups from the review of commit ae9aeea (`--sandbox` flag):

1. Failure messages still steer users to the legacy env var only: "Set CAKE_SANDBOX=off …" in `src/clients/tools/bash.rs` (~line 443, macOS sandbox-unavailable message) and `src/clients/tools/sandbox/linux.rs` (~lines 21-27, Landlock enforcement errors). Now that `--sandbox danger-full-access` is the discoverable surface, the hints should name the flag (env var may stay as a secondary mention).
2. `docs/design-docs/sandbox.md` policy table does not mention that settings.toml persistent read-write directories are demoted to read-only under the `read-only` policy. That is intended behavior but touches a documented compatibility surface ("settings directories grant persistent read-write access") and should be stated.
3. `BashExecutionArgs::from_json` hardcodes a `WorkspaceWrite` policy default that `execute_bash` always overwrites from the context; a future caller that forgets the override silently ignores the user's policy. Make the policy a required parameter (or construct args from context) to remove the foot-gun.
4. New sandbox tests swap `HOME` via `temp_env` while older sandbox tests read `HOME` without the temp_env lock — a low-probability parallel-test flake. Either route the older HOME-reading tests through temp_env or note why it is safe.

## Relevant Files

- `src/clients/tools/bash.rs`
- `src/clients/tools/sandbox/linux.rs`
- `src/clients/tools/sandbox/mod.rs` (tests)
- `docs/design-docs/sandbox.md`

## Acceptance Notes

- User-facing messages mention `--sandbox danger-full-access`.
- sandbox.md documents the settings-dirs demotion under read-only.
- Policy is explicit at `BashExecutionArgs` construction; no silent default path remains.
