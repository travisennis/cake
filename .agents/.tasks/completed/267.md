# Secure Bash overflow output temporary files on shared systems

## Summary

At commit `6e69b45`, Bash binary and overflow output is written beneath the predictable shared path `std::env::temp_dir()/cake`. On Linux this is normally `/tmp/cake`; default directory/file permissions and pre-creation by another local user can expose captured command output or redirect writes through an attacker-controlled path.

## Evidence

- `src/clients/tools/bash.rs:189-195` — binary output calls `create_dir_all(temp_dir()/cake)` and writes a UUID-named file without validating ownership or restrictive permissions.
- `src/clients/tools/bash.rs:490-496` — large text output uses the same directory and write pattern.
- `docs/design-docs/tools.md` documents these files as agent-readable overflow artifacts, so the replacement must preserve discoverability for the current invocation.
- macOS normally supplies a per-user `$TMPDIR`; the security impact is concentrated on multi-user systems where `temp_dir()` is a shared directory such as `/tmp`.

## Fix Direction

Use a securely created per-user/per-process temporary directory or equivalent ownership-checked location with restrictive permissions, and create output files without following attacker-controlled path state. Preserve the tool response's usable file path and allow the sandboxed agent to read the saved artifact. Scope this to Bash overflow/binary artifacts and any shared helper introduced for them; do not broaden sandbox write grants. If sandbox policy cannot access the secure location on both macOS and Linux, stop and report the required policy adjustment before weakening permissions.
