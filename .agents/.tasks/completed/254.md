# Gate macOS keychain write rules under the read-only sandbox policy

## Problem

Under `--sandbox read-only`, the macOS Seatbelt profile still grants `file-read* file-write*` on `~/Library/Keychains` via `append_keychain_rules` (`src/clients/tools/sandbox/macos.rs:218`). ADR-014 explicitly identified this class of hardcoded rule ("would otherwise re-grant writes that the partitioned SandboxConfig removed") and gated the SCM CLI rules (`append_scm_cli_rules`), but the keychain rule was missed. Result: a "read-only" session can write to user keychain database files.

The other ungated write grants are legitimately needed even in read-only mode and should stay: SSH agent sockets (connect requires write) and `/dev/*` devices.

## Fix Direction

Pass the same `read_only` flag to `append_keychain_rules` as `append_scm_cli_rules` receives, and emit `file-read*` for `~/Library/Keychains` when read-only. The `/Library/Keychains` and `/System/Library/Keychains` rules are already read-only.

## Relevant Files

- `src/clients/tools/sandbox/macos.rs` (`append_keychain_rules`, `generate_profile`)

## Acceptance Notes

- Profile-generation unit test: read-only config emits no `file-write*` rule for `~/Library/Keychains`; workspace-write profile unchanged.
- Security impact called out in handoff (closes a read-only write leak; no boundary relaxation).
