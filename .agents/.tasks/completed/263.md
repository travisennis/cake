# Bound Bash command lifecycle timeouts and terminate process groups

## Summary

At commit `6e69b45`, Bash tool timeouts cover pipe reads but not the final child wait. A command that closes both captured streams while continuing to run can therefore leave the agent turn waiting indefinitely, and timeout/cap cleanup targets only the direct child rather than its process group.

## Evidence

- `src/clients/tools/bash.rs:320-327` — Bash commands use piped stdout/stderr and `kill_on_drop(true)` on the direct Tokio child.
- `src/clients/tools/bash.rs:352-400` — `timeout(Duration::from_secs(args.timeout), ...)` wraps only the stdout/stderr read loop.
- `src/clients/tools/bash.rs:402-406` — after the timeout scope, cap handling calls `child.kill()` and then `child.wait().await` without a bound.
- Representative failure shape: a shell command redirects or closes both output streams and then waits on long-lived work, so the read loop reaches EOF before the process exits.

## Fix Direction

Make the configured Bash timeout cover the complete process lifecycle, including termination and reap, and ensure timeout/output-cap cleanup terminates the command's process group so descendants do not survive. Keep existing output formatting, timeout text, sandbox setup, and command-safety semantics unchanged. Scope changes to Bash process spawning/lifecycle and focused tests; do not redesign the general tool scheduler. If a cross-platform process-group strategy would change Windows support or require a new dependency, stop and document the options before expanding scope.
