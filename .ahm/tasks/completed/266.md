# Correct stale session persistence architecture invariants

## Summary

At commit `6e69b45`, `ARCHITECTURE.md` still describes session persistence as temp-file-plus-rename atomic writes and latest-session lookup as mtime-based. The implementation and accepted append-only session design instead use locked JSONL appends and select sessions from the `session_meta.timestamp`, so the architecture invariants currently give agents incorrect compatibility guidance.

## Evidence

- `ARCHITECTURE.md:78` --- invariant 6 says session writes use temp-file-plus-rename atomicity.
- `ARCHITECTURE.md:126-127` --- the data-flow section says save is atomic and latest-session lookup is based on mtime.
- `src/config/session.rs:248-289` --- new and existing sessions use locked append handles and newline-delimited record appends.
- `src/config/data_dir.rs:229-245` --- latest-session candidates are compared using timestamps read from session metadata.
- `docs/adr/004-append-only-session-task-events.md` and `docs/design-docs/session-management.md:245-247` --- accepted design explicitly defines append-only live persistence and partial-task recovery.

## Fix Direction

Correct the architecture invariant and session data-flow text to match the accepted append-only JSONL design, advisory locking, live record appends, and metadata-timestamp selection. Also correct the stale `src/config/data_dir.rs:151` doc comment if it still claims atomic save semantics. Do not change runtime behavior or session schemas. If another architecture statement intentionally distinguishes initial creation from continuation appends, retain that distinction explicitly.
