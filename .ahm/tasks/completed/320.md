# Narrow CRLF offset table elements to u32

## Summary

Task 313 made `NormalizedContent.original_offsets` optional (`None` = identity mapping for LF-only files), skipping the per-byte allocation entirely when no `\r\n` is present. For files that DO contain CRLF line endings, the offset table is still `Vec<usize>` — 8 bytes per normalized byte on 64-bit platforms.

Narrowing the element type from `usize` to `u32` would halve the offset table size (4 bytes per entry), which matters for large CRLF files. This requires:

- A documented file-size ceiling (u32 can represent offsets up to ~4 GiB).
- A fallback or explicit error for files exceeding the ceiling.
- Preserving byte-identical output for all files within the ceiling.

## Fix Direction

1. Change `original_offsets` from `Option<Vec<usize>>` to `Option<Vec<u32>>`.
2. In `normalize_crlf_line_endings`, check if `content.len() > u32::MAX as usize` and either fall back to a `Vec<usize>` path or return an error.
3. Update `original_offset` to cast `u32` back to `usize`.
4. Add tests: ceiling-respecting file works, ceiling-exceeding file has a defined outcome.

## Acceptance Notes

- [x] CRLF files under the ceiling produce byte-identical output to the current implementation: element width changed from `usize` to `u32` only; stored offsets and all consumers (`original_range`, `original_offset`, reverse-order application) are unchanged. Covered by existing CRLF/preservation tests plus a compile-time type pin (`assert_eq!(offsets[0], 0u32)`) in `crlf_content_uses_explicit_offset_table`.
- [x] Files above the u32 ceiling have a defined and tested outcome: explicit error from `check_crlf_offset_table_size` (extracted helper), exercised at the exact boundary (`MAX_OFFSET_TABLE_BYTES` ok, `+1` errors with a message naming the ceiling and file size). The 4 GiB ceiling is impractical to allocate in a unit test, so the check is tested directly rather than via a >4 GiB string; the wiring in `normalize_crlf_line_endings` runs before any table allocation. `#[expect(clippy::cast_possible_truncation, reason = ...)]` documents why the `as u32` casts are safe.
- [x] LF-only files remain unaffected (still `None`, no ceiling check, any size): verified by `lf_only_content_uses_identity_offset_mapping` and by inspection (identity path returns before the ceiling check).
