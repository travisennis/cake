# Grant Landlock Execute access on readable paths (read-only policy breaks exec on Linux)

## Problem

Landlock grants `readable` paths only `ReadFile | ReadDir` — no `AccessFs::Execute` (`src/clients/tools/sandbox/linux.rs:77`). The read-only policy (task 195) moves the workspace and all toolchain dirs from `writable` (which used `AccessFs::from_all`, including Execute) into `readable`. On Linux under `--sandbox read-only`, executing anything outside system paths fails: `~/.cargo/bin/cargo`, fnm/nvm-installed node, `./gradlew`, `node_modules/.bin/*`, workspace scripts. macOS is unaffected because Seatbelt `file-read*` plus the global `process-exec` allow is sufficient to exec.

This is the macOS/Linux divergence failure mode called out in `docs/guardrails/sandboxing-and-filesystem-boundaries.md`, and it contradicts ADR-014's cross-platform-parity driver. Pre-existing smaller instance: skill dirs and `--add-dir` paths are also in `readable`, so the comment "so scripts like x-fetch.js can execute" has never been true on Linux.

## Fix Direction

Grant `AccessFs::ReadFile | ReadDir | Execute` for `readable` paths in `apply_landlock_rules` (matching the `system_paths` treatment, which already adds Execute). Read-only means "no mutations", not "no execution" — execution of readable files does not relax the write boundary.

CI note: `cargo test` runs only on macOS (`.github/workflows/ci.yml`; Linux job is `cargo check` only), so state the platform verification gap in the handoff, or verify on a Linux machine/container if available.

## Relevant Files

- `docs/design-docs/sandbox.md` (platform behavior notes, if execute semantics are documented)
