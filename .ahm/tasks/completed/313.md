# Avoid the per-byte CRLF offset table for LF-only files

## Summary

At commit `e569256`, `NormalizedContent` allocates a `Vec<usize>` with one entry per normalized byte on every Edit, whether or not the file contains CRLF line endings. For the overwhelmingly common LF-only file the table is the identity mapping, and it costs 8 bytes per source byte — a 20 MB file spends 160 MB on the table alone, on top of the normalized copy.

## Problem

The offset table exists so that matches found in CRLF-normalized content can be mapped back to byte offsets in the original file. When the original contains no `\r\n`, normalization is a no-op and every entry satisfies `original_offsets[i] == i`, so the allocation is pure overhead proportional to file size.

## Evidence

- `src/clients/tools/edit.rs:126-135` — `NormalizedContent.original_offsets: Vec<usize>`, one entry per normalized byte.
- `normalize_crlf_line_endings` in `src/clients/tools/edit.rs` populates the table unconditionally.
- Task 076 (Optimize Edit Application Allocation, completed) covered edit *application*; this is the normalization input side and was not in its scope.

## Fix Direction

Short-circuit when the content contains no `\r\n`: represent the mapping as identity and skip both the table and the normalized copy. Narrowing the offset element type to `u32` (with a documented file-size ceiling and a fallback or explicit error above it) is a reasonable additional halving for the CRLF case, but the identity short-circuit is the change that matters and should land first.

Preserve exactly the current line-ending behavior: CRLF files keep their line endings, mixed-ending files behave as they do today, and reported match offsets stay correct. Task 036 and task 109 established these semantics — do not regress them.
