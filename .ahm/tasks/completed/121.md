# Implement User-Defined Toolbox Tools

**Source:** Completed ExecPlan `toolboxes-plan.md`

**Priority:** P2

**Effort:** XL

**ExecPlan:** `.ahm/exec-plans/completed/toolboxes-plan.md`

**ADR:** [ADR-017: Trusted Executable Toolbox Tools](../../../docs/adr/017-trusted-executable-toolbox-tools.md)

**Depends on:** 050 (Backend abstraction, completed), 051 (Tool abstraction, completed)

**Problem:** Cake has four hardcoded tools (Bash, Read, Edit, Write). Users cannot extend the tool set with custom executables. Other agent CLIs support user-defined tools via a simple stdin/stdout protocol.

**Files involved:** `src/config/toolbox.rs` (new), `src/clients/tools/toolbox.rs` (new), `src/clients/tools/mod.rs`, `src/clients/agent.rs`, `src/cli/mod.rs`, `src/main.rs`

**Fix:**
1. **Discovery**: Scan `CAKE_TOOLBOX` colon-separated directories (default `~/.config/cake/tools/`) for executable files, skipping hidden files, `.md`/`.txt`, non-executables, and directories.
2. **Describe protocol**: Run each executable with `TOOLBOX_ACTION=describe` to get name, description, and parameter schema. Support both JSON format (compact `args` and full `inputSchema`) and text format. Skip broken tools with a warning.
3. **Execute protocol**: Dispatch `tb__*` tool calls by running the executable with `TOOLBOX_ACTION=execute`, passing arguments on stdin, capturing stdout, and checking exit codes.
4. **Agent integration**: Register toolbox tools as `ToolEntry` values in the existing `ToolRegistry` (task 051). `ToolExecutor` is currently a plain `fn` pointer, which cannot carry per-tool state (path, format, timeout) — widen it to `Arc<dyn Fn(...)>` or equivalent. Inject via an `Agent::with_*` builder method (constructor is `Agent::new(config, initial_messages)`).
5. **CLI**: Add `--toolbox <DIR>` flag and optional `Tools` variant in the `Commands` enum (`src/cli/mod.rs`, `CmdRunner` pattern) with list, show, use, make.

Toolbox tools run as separate processes without sandboxing — they are user-provided and trusted. Under `SandboxPolicy::ReadOnly` they must be excluded from the registry (same rationale as `retain_read_safe_tools()` removing Edit/Write: they bypass the OS sandbox, so offering them would break the policy's no-mutation guarantee).

Additional current-code integration points: `format_tool_list_section()` builds the system-prompt tool list from `default_tool_registry()` and states "Only these tools are available" — it must reflect registered toolbox tools; `tb__*` calls flow through PreToolUse hooks and `schedule_tool_calls()` like built-ins (they get singleton scheduling groups since `mutating_target()` cannot see their targets).

**Status:** Complete. The toolbox feature, review fixes, documentation, ADR, and verification are finished. The optional `cake tools` management subcommands were explicitly excluded from this task's completed core scope.
