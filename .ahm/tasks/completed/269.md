# Detect committed work in generated worktrees without an upstream

## Summary

At commit `6e69b45`, cake decides whether a generated worktree contains commits by comparing `@{upstream}..HEAD`. Worktrees created from the documented `HEAD` fallback, or in repositories with automatic upstream setup disabled, have no upstream; committed-only work is then reported as unchanged and the worktree directory is removed even though the commit survives only on the generated branch.

## Evidence

- `src/config/worktree.rs:67-102` — when no default remote branch exists, creation falls back to `HEAD`.
- `src/config/worktree.rs:129-144` — the generated branch start point is used for `git worktree add` but is not persisted for later change detection.
- `src/config/worktree.rs:163-194` — after a clean porcelain status, `has_changes` runs `git log @{upstream}..HEAD` and returns `false` on any missing-upstream/error path despite the comment saying it checks commits ahead of the start point.
- `src/main.rs:1103-1108` — a false result drives the user-facing "No changes detected" removal path.
- Existing tests cover clean and uncommitted worktrees but do not commit work in a no-upstream worktree before calling `has_changes`.

## Fix Direction

Track or derive a stable comparison point that works with and without a configured upstream, and use it when deciding whether committed work exists. Preserve cleanup of truly unchanged generated worktrees and retention of any worktree with uncommitted or committed work. Keep branch deletion/error behavior explicit; do not silently discard the only convenient checkout of committed work. If reliably deriving the original start point requires persisted metadata, stop and evaluate the compatibility/location choice before adding a new durable file.

## Trade-off

Path 3 (minimal safe fix) was chosen after review cycles showed that any persisted-metadata
approach has a fundamental design flaw: the sandbox must grant write access to the git common
dir for tools (`git commit`, `git add`, etc.), so any metadata stored there is also tool-writable
and can be tampered with. The error-on-indeterminate approach is the simplest correct fix:

- **Wins**: Zero new state, zero CRAP regression, no symlink/race/metadata-corruption surface.
  Fixes the original bug (no silent deletion of committed work) with a 2-line change.
- **Loss**: Clean no-upstream worktrees are never auto-removed. They produce a warning log and
  are retained. A future Path 1 (external metadata store) can restore auto-cleanup if needed.
