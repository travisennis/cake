# Surface Cut-Off Outcome in JSON Mode Output and Telemetry

**Created:** 2026-07-09
**Source:** 2026-07-09 code review of commit 6acfdd0 (task 243 follow-up).

## Problem

Task 243 added `TaskOutcome::CutOff` so the harness stops fabricating assistant prose, but the conversion in `execute_agent_turn` (`src/main.rs`, around line 747) turns the `CutOffError` into `Ok(detail)` before rendering. Three surfaces still misreport cut-offs as success:

- **JSON mode:** `turn_result_json` (`src/cli/output.rs`, around line 131) puts any `Ok` value into `"result"` with no `"error"` field and exit code 0. A JSON consumer sees `{"result": "The model's response was cut off during reasoning."}` — harness-authored prose in the model-output position, indistinguishable from a real answer. This is the exact problem task 243 set out to fix, relocated to the JSON stdout payload. The session file records `CutOff`, but the JSON payload does not.
- **Telemetry:** `emit_session_summary_telemetry` (`src/main.rs`, around line 968) sees the converted `Ok` and logs `success=true` with no error string, so telemetry cannot distinguish cut-offs from clean completions.
- **Text mode (minor):** the detail prints unattributed in the assistant-output position. Task 243's acceptance note said the explanatory line should be attributed to cake, not rendered as an assistant message.

Stream-json is already correct (emits `task_complete` with `subtype: cut_off`, `is_error: true`; exit 0 matches the documented in-stream-error policy in `src/cli/output.rs`).

## Decision

Recorded 2026-07-09 with maintainer during grooming:

- **Exit code: 1 in both JSON and text modes.** A cut-off means no answer was produced, so automation sees failure. `CutOffError` falls through `exit_code::classify` to `AGENT_ERROR` (1) already. Stream-json keeps its documented in-stream-error policy of exit 0 (unchanged).
- **JSON payload shape: `"result": null`, `"error": <detail>`, plus an additive `"subtype": "cut_off"` field** so consumers can distinguish cut-offs from other agent errors — parity with stream-json's `task_complete` subtype. No changes to the successful-turn shape.
- **Implementation direction: stop converting the cut-off to `Ok(detail)`** in `execute_agent_turn` (`src/main.rs:759`, `let render_result = cut_off_detail.map_or(result, Ok)`); let `Err(CutOffError)` flow into `TurnResult` and have each render mode downcast. The existing plumbing then does most of the work: JSON mode's `result.map(|_| ())` propagates to `exit_code::classify` → 1; telemetry's `turn.result.is_ok()` naturally reports `success=false` with the detail as the error string; stream-json's `stream_json_exit_result` already ignores non-schema errors (exit 0 preserved). No new enum on `TurnResult` needed.
- **Text mode: the error propagates to `write_error`**, printing `Error: <detail>` on stderr — attributed to cake, out of the assistant-output position. No bespoke prefix needed.

## Fix Direction

- Remove the `cut_off_detail` → `Ok(detail)` conversion in `execute_agent_turn`; keep `handle_agent_turn_result` emitting the `TaskOutcome::CutOff` record as it does today.
- JSON mode: in `turn_result_json`, downcast the error to `CutOffError` and emit `"result": null`, `"error": <detail>`, `"subtype": "cut_off"`. This is a documented machine-readable compatibility surface: the change is additive and must be documented in `docs/design-docs/streaming-json-output.md` / `docs/design-docs/cli.md` as appropriate, including the exit-code table if cut-off warrants a note.
- Telemetry: falls out of the conversion removal — `success=false` with the detail string.
- Text mode: falls out of the conversion removal — stderr `Error:` line, exit 1.

## Relevant Files
