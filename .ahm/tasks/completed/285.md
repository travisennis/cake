# Harden the sandbox profile temp directory like the Bash output directory

## Summary

At commit `c0b7faa`, macOS Seatbelt profiles are written under the shared, predictable path `env::temp_dir()/cake/sandbox_profiles` with no ownership or permission validation. The Bash output directory (`bash_temp_output_dir`) was hardened against pre-creation attacks on shared sticky-bit temp dirs — random 64-bit suffix, uid check, 0700 enforcement, symlink detection — for exactly this class of attack, but the profile directory was not. A local attacker who pre-owns `/tmp/cake` can at minimum deny profile creation, and plausibly swap the profile file between cake writing it and `sandbox-exec` reading the path, weakening the sandbox that is supposed to constrain model-generated commands.

## Evidence

- `src/clients/tools/sandbox/macos.rs:349-357` — `write_profile_to_temp` uses `env::temp_dir()/cake/sandbox_profiles` with plain `create_dir_all`.
- `src/clients/tools/sandbox/macos.rs:47` — the probe uses the same unvalidated directory.
- `src/clients/tools/bash.rs:200-313` — `bash_temp_output_dir`/`ensure_secure_temp_dir` implement the hardened pattern, with comments describing the threat model.
- `sandbox-exec` consumes the profile by path (`macos.rs:420`), so the open `NamedTempFile` handle does not protect against a path swap in an attacker-owned parent directory.

## Fix Direction

Route sandbox profile files (and the probe file) through the same secure per-user directory mechanism used by `bash_temp_output_dir`, or extract that helper into a shared location and reuse it. Fail closed: if the secure directory cannot be created or validated, sandbox application should error rather than fall back to an unvalidated shared path. Consider that task 268 (profile temp file cleanup, completed) touched this area; keep its cleanup behavior.
