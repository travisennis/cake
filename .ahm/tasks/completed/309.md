# Repair Incomplete Tool Calls When Restoring Sessions

## Summary

At commit `fe8dd67`, make resumed sessions safe when a prior process ends after persisting a `FunctionCall` but before persisting its matching `FunctionCallOutput`. Repair incomplete call/output pairs with an explicit failed output before the next provider request, while preserving the append-only session format and existing CLI interrupt behavior.

## Problem

Cake persists model turn items before executing their tools. If Cake is interrupted, crashes, or is killed in that interval, the session can end with a model function call that has no corresponding output. Resume currently restores that conversation verbatim and appends a new user message. OpenAI-compatible providers can reject the resulting request because an assistant tool call is not followed by its tool result, turning the session most worth recovering into an HTTP 400 failure.

## Evidence

- `src/clients/agent/agent_loop.rs:91-97` extracts, streams, and adds model turn items to the conversation before tool execution begins. Tool execution starts later around lines 133-134, and output items are created and streamed around lines 302-319.
- `src/clients/agent/observer.rs:24-33` persists streamed conversation records as they arrive, so the function call can be durable before its output exists.
- `src/main.rs:1004-1030` drops the in-flight turn future when Ctrl-C wins the `select!`. The interrupt path around lines 1055-1098 records task completion and telemetry but does not close outstanding function calls.
- `src/clients/agent_state.rs:45-67` restores stored conversation history without validating call/output pairing.
- `src/clients/chat_completions.rs:172-177` accumulates pending tool calls, and lines 285-314 can flush them into an assistant message before a later user message without inserting a tool result. The Responses backend must also receive valid restored call/output ordering.
- `src/clients/agent/agent_loop.rs:116-124` already uses explicit failed `FunctionCallOutput` items to keep the live conversation well formed when a model turn needs correction; restoration should use the same semantic precedent.
- The local 14-day telemetry sample contained 5 abnormal-termination candidates among 225 invocations. That does not prove all five hit this race, but it establishes that abrupt endings are not merely theoretical.

## Fix Direction

When restoring a persisted conversation, validate every function call identifier against subsequent function-call outputs before appending the next user turn. For each unambiguous unmatched call from the prior run, materialize an ordinary failed `FunctionCallOutput` whose content clearly states that the tool was not executed or its result was not recorded because the prior Cake process ended. Never represent the tool as successful and never execute the abandoned call during resume.

Add the repair items to the in-memory conversation and append them through the existing conversation-record path before the next provider request so later resumes see the same well-formed history. Preserve every existing byte in the session JSONL; restoration may append but must never rewrite or delete prior records. Use the existing serialized item shape rather than introducing a new session-record version or repair-only wire type.

Apply the invariant at the shared conversation/session boundary so both Chat Completions and Responses backends receive valid history. Keep provider-specific request shaping at each backend boundary. If duplicate call identifiers, an output before its call, or another corruption makes pairing ambiguous, stop with a precise local session diagnostic rather than guessing which call an output belongs to.

This task does not redesign cancellation, make tool execution transactional, change Ctrl-C exit code 130, alter task-completion records, or recover a tool result that may have happened outside Cake without being persisted. If satisfying the fix requires rewriting session history, a new persisted record type/version, or a provider-specific interpretation that cannot share the same restored conversation, stop and record a compatibility decision before implementation.

### Implementation Summary

- `ConversationState::with_restored_history` validates call/output pairing on the restored slice, appends a failed `FunctionCallOutput` for each still-open call, and queues those items for persistence. Ambiguity (two open calls sharing a `call_id`, or an output with no open call) aborts restoration before any history is mutated.
- `Agent::emit_history_repair_records` streams and persists the queued items; `execute_agent_turn` calls it after `task_start` and before `send`, so both Chat Completions and Responses receive repaired history and later resumes read it back matched.
- A `call_id` reused after its output closed is explicitly allowed, so providers that number calls per request still resume.
