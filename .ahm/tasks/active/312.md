# Bound Read tool memory and I/O for large files

## Summary

At commit `e569256`, the Read tool still does work proportional to the *file* rather than to the requested window in two ways: it buffers the entire requested line range in memory before applying `MAX_OUTPUT_BYTES`, and it reads to EOF on every call solely to compute an exact total line count. Task 265 removed per-line allocation for lines *outside* the window and fixed byte-boundary truncation; these two costs remain.

## Problem

**Memory.** `end_requested` is taken from the model's `end_line` with no clamp. Every line in `[start, end_requested]` is pushed as an owned `String`, `join("\n")` allocates the concatenation a second time, `format!` allocates a third, and only then does the byte cap apply. `{"path": "big.log", "end_line": 99999999}` against a 500 MB file peaks well over 1 GB of resident memory before returning roughly 100 KB. This is reachable from ordinary model output — no adversarial input required.

**I/O.** The counting loop always runs to EOF so the header can report an exact `total_lines`. Reading lines 1-200 of a 2 GB log reads all 2 GB. The only consumers of the exact count are the `Lines a-b/total` header and the `[... N more lines ...]` footer.

## Evidence

- `src/clients/tools/read.rs:120-127` — `end_requested` derives directly from `end_line` with no upper clamp.
- `src/clients/tools/read.rs:140-163` — the loop runs to EOF unconditionally; in-window lines are pushed as owned `String` values with no running byte budget.
- `src/clients/tools/read.rs:177-184` — `join("\n")` plus `format!` reallocate the accumulated window twice more.
- `src/clients/tools/read.rs:186-203` — `MAX_OUTPUT_BYTES` truncation runs only after all of the above.
- `src/clients/tools/read.rs:205-212` — `total_lines` is consumed by the remaining-lines footer.

## Fix Direction

Stop accumulating once the running byte total for in-window content exceeds `MAX_OUTPUT_BYTES` (plus the truncation-marker reserve), and stop reading once neither the window nor the pagination signal needs more input. Building the output incrementally into a single `String` removes the double reallocation at the same time.

Total-line reporting is the compatibility question. The Read output header and footer are model-visible text with snapshot coverage, so decide explicitly rather than silently: either keep an exact count only when the file was already read to EOF and switch to an unambiguous "at least N" / "more lines follow" phrasing otherwise, or cap the counting pass at a bounded number of lines past the window. Whichever is chosen, the phrasing must not let the model conclude a file is shorter than it is, and `read-description.txt` plus affected snapshots must be updated together.

Do not add caching, indexing, or a new pagination parameter under this task.

## Acceptance Notes

- [ ] A huge `end_line` against a large file returns within the documented byte cap without buffering the whole requested range — a test asserts bounded allocation or bounded read volume, not just correct output.
- [ ] Reading an early window of a large file does not read to EOF.
- [ ] The total-lines decision is recorded in the task or in `read-description.txt`, and the model-visible header/footer text can never understate file length.
- [ ] Existing range, default-window, line-numbering, multibyte-truncation, and binary-rejection tests still pass; tool snapshots are updated deliberately if the header or footer text changes.
- [ ] `cargo test read` and `just ci` pass.
