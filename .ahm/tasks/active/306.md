# Establish a Controlled Model Evaluation Harness

## Summary

At commit `fe8dd67`, Cake has strong operational telemetry but no controlled way to compare whether configured cheap or local models complete the same coding tasks correctly. Establish a repository-local evaluation harness that runs identical fixture tasks across model configurations and judges results with deterministic verifier commands. Keep this as contributor tooling rather than adding a new Cake product command or interactive surface.

## Evidence

- `scripts/session-metrics/README.md:22-30` lists reports for tokens, tools, API reliability, timing, runtime outcomes, and hooks, but no controlled task-quality evaluation or repeatable model comparison.
- `scripts/session-metrics/outcomes.py:18-25` counts a task as successful when its transcript subtype is `success`; this proves the agent loop ended normally, not that the produced repository state is correct.
- `scripts/session-metrics/report.py:20-24` composes only operational report modules. There is no fixture runner, deterministic correctness oracle, repeated-trial support, or model matrix.
- The 2026-07-27 local 14-day audit showed materially different Edit failure rates by model (12.2% for `deepseek-v4-flash`, 4.1% for `kimi-k2.7-code`), but those sessions used different tasks, so the result cannot establish comparative model or harness quality.
- `README.md:1-3` defines Cake as a headless Unix-filter-style coding assistant. The evaluation design must preserve that product shape: no REPL, TUI, daemon, or benchmark-specific behavior in the production agent loop.

## Fix Direction

Add a small `scripts/evals/` harness, following the repository's existing stdlib-oriented Python tooling style, plus a `justfile` recipe. Define committed fixture cases with an initial Git repository state, a task prompt, a trusted verifier command, timeout/tags, and optional expected file constraints; copy each fixture into an isolated temporary repository before invoking Cake. Run a selected configured model for one or more repetitions using Cake's existing machine-readable completion output, and record verifier pass/fail separately from provider, Cake, timeout, or harness failures together with turns, tool calls, token usage, duration, and model name.

The first suite should contain a small representative set rather than attempting an external leaderboard: repository discovery, targeted single-file edit, stale-context-sensitive edit, multi-file change, and test-driven correction are sufficient. Use deterministic repository-owned verifier commands as correctness oracles; do not use an LLM judge. Generated transcripts, patched worktrees, and potentially sensitive model output must remain in ignored temporary/result locations, while an aggregate JSON result schema and concise human table may be retained.

Files in scope are `scripts/evals/` (new), focused fixtures under a clearly named test-data directory, `justfile`, and concise contributor documentation. Production Rust, the public CLI, system prompt, default model selection, and provider behavior are out of scope. If a proposed fixture has no deterministic oracle, exclude or redesign it; if running a real model would require unavailable credentials or unapproved external spend, STOP and report that constraint rather than fabricating a result.

Match repository conventions: keep scripts dependency-free when practical, keep machine-readable stdout stable, distinguish operational failure from incorrect output, preserve unrelated worktree state, and use `just ci` as the final code/config gate.

## Acceptance Notes

- [ ] A documented fixture format represents initial repository state, prompt, trusted verifier, timeout/tags, and expected outcome without embedding credentials or machine-specific absolute paths.
- [ ] The runner executes every case in an isolated temporary Git repository and leaves both the Cake source tree and fixture sources unchanged, including on failure or interrupt.
- [ ] Model selection and repetition count are explicit inputs; the same case is presented identically to every selected model.
- [ ] Stable JSON results distinguish `correct`, `incorrect`, `cake_error`, `provider_error`, `timeout`, and `harness_error`, and include turns, tool calls, duration, and available usage fields.
- [ ] A human summary reports correctness rate and median/p90 turns, tokens, duration, and tool failures by model and case tag without treating Cake's `success` subtype as correctness.
- [ ] At least five representative deterministic cases are committed. No fixture uses an LLM judge or relies on network access in its verifier.
- [ ] Automated tests use a fake Cake executable and temporary fixtures to cover a correct result, verifier failure, malformed completion JSON, timeout, repeated trials, and cleanup. Add them under `scripts/evals/tests/` and expose one exact `just` check command.
- [ ] Run the fake/deterministic harness check and expect all cases to pass. Run at least one real configured model if credentials and cost authorization are available; otherwise record the exact blocker and the command a maintainer can run later.
- [ ] Document that this is contributor tooling, not a supported `cake eval` CLI contract, and document where generated results live and how they are ignored.
- [ ] Run `just ci` and expect all checks to pass.
