# Flatten Edit tool arguments to a single-edit schema

## Blocker

Deferred by the 2026-07-07 backlog triage decision: leave the Edit schema
alone and measure first. The failure data below predates commit `384401c`
(2026-07-06), which shipped JSON repair plus caret-context parse errors
aimed at exactly the seam failures cited here. Re-run the Edit-failure
analysis on ~30 days of post-`384401c` telemetry (early August 2026). If
invalid-JSON failures have collapsed, cancel this task; if they persist,
write the ADR below. The ADR must decide whether the duplicate-mutation
guard semantics stay as-is for sequential same-file edits (note: the guard
is being replaced by per-path serialization per the same triage), document
the loss of multi-edit atomicity, and record why the flat
`{path, old_text, new_text}` schema is preferable to keeping the nested
shape with an argument-repair layer or moving to a patch-string format.

## Problem

The Edit tool's argument shape is `{path, edits: [{old_text, new_text}, ...]}` with up to 20 edits per call. Session-transcript analysis (30 days, 195 sessions, 1,084 Edit calls, 11.7% failure rate) shows this nested shape is directly implicated in the invalid-JSON failure category (~60 calls, ~half of all failures):

- Models frequently emit the `edits` array first and `path` last. After generating a multi-KB escaped blob, they must land the `"}], "path": ...` seam exactly — and structural failures cluster right there: double commas (`}],,`), doubled closing braces (trailing characters), a dropped closing quote just before `}]`, and 6 calls that omitted `path` entirely.
- The batching capability is barely used: 83% of successful calls (785/941) contain exactly one edit, 92% contain one or two, and no observed call exceeded 11. The nested array-of-objects shape imposes its syntactic overhead on every call to serve a minority use.

A flat schema `{path, old_text, new_text}` removes the seam entirely, shrinks payloads, and is substantially simpler to maintain (no multi-edit preflight summary, no overlap detection, no no-op index bookkeeping, no reverse-order application).

## Trade-offs and Decision Scope

- Multi-edit batches become sequential calls. The duplicate-mutation guard (`src/clients/tools/duplicate_guard.rs`) rejects a second same-file mutation within one assistant turn, so what was one batched call becomes one call per turn — more turns for the ~17% of calls that batch today. Decide whether the guard's semantics stay as-is (recommended: yes, it exists to prevent stale-content edits) or are revisited.
- This changes the tool schema and tool execution semantics — declared compatibility surfaces. The atomicity guarantee ("all edits succeed or none apply") disappears as a concept since a call carries one edit.
- Model-facing description (`edit-description.txt`), guidance about batching in system prompts, and design docs all reference the multi-edit shape.

**An ADR is required before implementation** (durable change to a tool contract). The ADR should record the data above, the alternatives (keep nested shape + repair layer; patch-string format), and the decision.

## Fix Direction

1. Write the ADR; get it accepted.
2. Change the schema to `{path, old_text, new_text}` (all required, `additionalProperties: false`). Keep exact-match-exactly-once semantics, line-ending/BOM handling, diff output, and `mutating_target` unchanged.
3. Delete multi-edit machinery: `MAX_EDITS_PER_CALL`, preflight failure summary, overlap rejection, no-op index lists, reverse-order application. Retain the single no-op case (`old_text == new_text`) as a reported no-op.

5. Sessions persist tool schemas per `session_meta`; confirm resuming an old session with old-shape `function_call` records in the transcript replays without error (transcript records are history, not re-executed — verify this assumption).

## Failure taxonomy now (128 failures / 1,116 calls)

  | Class                              | Count | Share of failures |
  | ---------------------------------- | ----- | ----------------- |
  | `old_text` not found (no match)    | 77    | 60%               |
  | Invalid edit arguments             | 30    | 23%               |

  | Other (path, overlap)              | 2     | 2%                |

Within the 30 invalid-argument failures, 12 are a *field-name* error rather than a JSON structural error: 7 sent `new_string` instead of `new_text`, plus `new_head`, `new_name`, and 2 that sent `path` where it was rejected as unknown. 4 omitted `path` entirely (down from 6). JSON repair cannot fix a wrong field name — that residue is a schema-affordance problem, not a seam problem.

## The finding that changes the decision scope

`no_match` is now the dominant failure class, and its root causes are not schema-shaped:

- **31 of 77** `no_match` failures are *stale-after-own-edit*: the agent successfully edited a file, then issued a later edit whose `old_text` was drawn from a view predating its own earlier edit. `e1b96a59` hit this five times on `src/hooks.rs` alone.
- **34 of 35** `no_match` failures that had a `Read` within two calls followed a *partial/ranged* read — the model composed `old_text` covering material it never actually saw. Corpus-wide, **63.4% of all Read calls return truncated content** (1,522 of 2,400).

Flattening the schema does not address either. This is directly relevant to the trade-off the blocker asks the ADR to settle — whether the duplicate-mutation guard semantics stay as-is for sequential same-file edits. The staleness data is evidence *for* the guard's stated rationale ("it exists to prevent stale-content edits"): the failure it guards against is real and is now the single largest Edit failure mode.

Note this cuts against flattening on one axis: a flat schema converts today's ~18% batched calls into sequential same-file calls, which is exactly the pattern that produces stale-content edits, and per-path serialization (task 236) changes the turn economics of that conversion.

## Suggested disposition

Neither "cancel" nor "write the ADR as scoped" is quite right. The ADR's original framing — invalid-JSON seam failures justify flattening — is now supported by roughly half the evidence it was written against, while the batching argument (simplicity, 82% single-edit) is fully intact and independent of the JSON data. If the ADR proceeds, it should be re-scoped to decide on simplicity/maintenance grounds and to record that the dominant failure mode has moved to content staleness, which a schema change does not fix.
