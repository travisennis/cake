# Decide whether Bash commands inherit cake's provider API key

## Summary

At commit `e569256`, the Bash tool spawns `bash` with the full parent environment, which includes cake's own provider credential (`OPENAI_API_KEY`, or whatever `api_key_env` names for the active model). The macOS Seatbelt profile allows network access, so a single model-generated command can exfiltrate cake's provider key.

This is a **design decision to make explicitly**, not a gap to patch silently — `docs/security.md` currently scopes this behavior out, and changing it changes documented security posture.

## Problem

`docs/security.md:36` states that commands may reach remote services using credentials readable within their environment. That is a deliberate and reasonable stance for *the user's* credentials: tools legitimately need `GITHUB_TOKEN`, cloud credentials, and registry tokens to do their job, and stripping them would break ordinary work.

Cake's own provider key is different in kind. No Bash command has a reason to read it, so removing it costs nothing in capability while closing a specific prompt-injection path: an injected instruction in fetched content can `curl` the key to an attacker-controlled host in one call, and the sandbox permits the network egress.

The counter-argument deserves weight: a user may deliberately want a nested cake invocation, or a script that calls the same provider, to inherit the key. Removing it changes that behavior. That is why this is filed as a decision rather than a one-line change.

## Evidence

- `src/clients/tools/bash.rs:372-379` — `Command::new("bash")` is configured without `env_clear` or any `env_remove`, so the child inherits everything.
- `src/clients/tools/sandbox/macos.rs:280` — the Seatbelt profile includes `(allow network*)`.
- `src/config/model.rs` — `api_key_env` names the variable, so the exact variable to strip is known at tool-execution time via the resolved model config.
- `docs/security.md:36` — the current documented scope explicitly covers credentials readable in the command environment.

## Decision To Make

Choose one and record the outcome:

1. **Strip cake's provider key from tool child environments.** `command.env_remove(&config.model_config.api_key_env)` on the Bash path, and any other path that spawns a child from model-controlled input. Defense in depth at essentially zero cost, but nested cake invocations lose the inherited key unless the user re-exports it.
2. **Strip it by default, with an opt-out.** Same default as (1), with a settings key for users who want the inheritance back. More mechanism to maintain.
3. **Keep current behavior and document it specifically.** Make `docs/security.md` say plainly that cake's own provider credential is readable by model-generated commands, rather than leaving it implied by the general credentials sentence.

Option 1 is the recommendation. Whatever is chosen, `docs/security.md` should end up stating the actual behavior for cake's own key rather than only the general case.

## Scope Notes

If option 1 or 2 is taken: apply it wherever cake spawns a child process from model-controlled input, not just the Bash tool — check the toolbox execute path and hook invocation, and note that hooks are trusted extensions and may legitimately differ. Do not attempt to strip the user's other credentials under this task; that is a much larger policy change and would break ordinary tool use. Do not weaken or alter the sandbox network policy here.
