# Bound per-turn tool and hook concurrency

## Summary

At commit `e569256`, a turn fans out over every pre-tool hook and every scheduling group with `futures::future::join_all` and no concurrency limit. A model turn containing 100 `Bash` calls spawns 100 concurrent `sandbox-exec` children at once, each holding a Seatbelt profile temp file and up to `BASH_READ_CAP` of buffered output.

## Problem

`join_all` starts every future immediately. The number of in-flight tool executions is therefore whatever the model emitted in one turn, with no ceiling. Each concurrent `Bash` call carries a child process, a process group, a sandbox profile file, and its output buffers; each pre-tool hook carries a child process of its own. On a large turn this shows up as process-table and file-descriptor pressure and as a memory spike proportional to the turn's tool-call count.

ADR 013's guarantee is only about *ordering* — mutating calls against the same canonical path run sequentially in issue order. It says nothing about how many independent groups may run at once, so adding a ceiling does not change the documented scheduling contract.

## Evidence

- `src/clients/agent/agent_loop.rs:172` — `join_all(pre_futures)` over every pre-tool hook.
- `src/clients/agent/agent_loop.rs:199-212` — `join_all(group_futures)` over every scheduling group produced by `schedule_tool_calls`.
- `docs/adr/013-per-path-serialization-of-mutating-tool-calls.md` — the invariant is per-path ordering, not unbounded parallelism.
- Results are re-sorted by issue index after the join, so a bounded execution order does not affect the order the model sees.

## Fix Direction

Replace the unbounded joins with a bounded concurrent execution — `futures::stream::iter(...).buffer_unordered(limit)` over the same futures, or a semaphore held across each group — for both the hook fan-out and the group fan-out. Keep result collection and the final sort by issue index exactly as they are so the model-visible ordering of tool results is byte-identical.

Pick the limit deliberately and record the reasoning. A small fixed value is likely right; deriving it from available parallelism is also defensible. If it becomes a settings key it belongs under the `[limits]` section proposed in task 238 rather than as a new top-level key — coordinate with that task rather than inventing a parallel mechanism.

Sequencing within a group must remain strictly sequential in issue order, and a slow call in one group must not be able to starve others into a deadlock — verify the bounded form cannot serialize a group behind itself.
