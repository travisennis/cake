# Add Criterion Benchmarks for Hot Per-Tool-Call Paths

**Source:** 2026-08-01 comparison of cake against `nanochat-rs`
(`~/Projects/coding-agents/nanochat-rs`), whose `benches/benchmarks.rs` uses
Criterion with `Throughput` accounting and a tuned `custom_criterion()` config.
Cake has no equivalent.

## Problem

Cake has **zero performance measurement**. There is no `benches/` directory, no
`[[bench]]` target in `Cargo.toml`, no `cargo bench` recipe in the `justfile`,
and no timing assertion anywhere in the 1,153-test suite.

CI gates correctness (`test-all-features`), coverage and untested complexity
(`check-coverage`, `ci/cargo-crap-baseline.json`), module size, import
direction, and dependency direction. Nothing gates latency. A quadratic
regression in code that runs on every single tool call would pass `just ci`
unnoticed.

The exposed paths, in descending order of per-call frequency:

  | Path | Entry point | Runs on |
  | --- | --- | --- |
  | Command safety guard | `bash_safety::validate_command_safety` (`src/clients/tools/bash_safety/mod.rs:115`) | every model-generated Bash call |
  | Shell parsing primitives | `parse::strip_shell_data`, `split_segments`, `extract_command_substitutions` (`src/clients/tools/bash_safety/parse.rs:265,24,219`) | every Bash call, several times each |
  | Unified diff generation | `generate_unified_diff` (`src/clients/tools/edit.rs:843`) | every Edit call |
  | Tool-argument repair | `json_repair::repair_json_args` (`src/clients/tools/json_repair.rs:29`) | every malformed tool call |
  | Session record conversion | `SessionRecord::from_conversation_item` / `to_conversation_item` (`src/types/session.rs:407,486`) | every record written and every record replayed on `--resume` |

`bash_safety` is the sharpest case: 2,124 lines across `checks.rs` (1,119) and
`parse.rs` (1,005), running a registry of checks over every command, with each
check re-scanning the normalized string. Session replay is the sharpest
*scaling* case, since transcript length grows without bound across
`--continue` runs.

## Blocking constraint: cake has no library target

This is the thing that makes the task non-trivial, and it must be settled
before any benchmark is written.

Criterion benchmarks in `benches/` compile as **separate crates** that link
against the package's **library** target. Cake has no `src/lib.rs`; it is a
binary-only crate (`src/main.rs:3-12` declares `mod cli; mod clients; mod
config; ...` — all private). `ARCHITECTURE.md` states "Cake is a binary crate"
as a durable fact, and `Cargo.toml` justifies `missing_docs = "allow"` with
"Binary crate - missing_docs produces noise without producing useful public API
docs."

So `use cake::clients::tools::bash_safety::...` from a bench does not compile
today, and cannot be made to compile without a decision.

### Option A — add a library target (recommended)

Standard Rust lib+bin split:

1. Add `src/lib.rs` declaring the existing modules (`pub mod cli;`, `pub mod
   clients;`, ...). Module bodies do not move and internal `crate::` paths keep
   working unchanged, so `just lint-imports` and `just lint-deps` stay green.
2. Reduce `src/main.rs` to a thin binary that calls into the library.
3. Raise the specific benchmark entry points from `pub(super)`/private to
   `pub`, leaving their **modules** private, then re-export exactly those items
   from a `#[doc(hidden)] pub mod bench_api` in `lib.rs`.

   Note the Rust rule here: `pub use` cannot widen visibility (E0365). A
   `pub(super) fn` cannot be re-exported. The item itself must become `pub`
   while its containing module stays private — that keeps it unreachable via
   any normal path while still allowing the `lib.rs` facade to re-export it.
   `generate_unified_diff` (`src/clients/tools/edit.rs:843`) is currently
   module-private and needs the same treatment.
4. Gate `bench_api` behind a `bench` Cargo feature so the exposed surface is
   not a standing commitment. Confirm `just clippy-no-default-features` and
   `just test-all-features` both still pass, since CI runs both ends of the
   feature matrix.

**Cost:** touches `ARCHITECTURE.md` ("Cake is a binary crate"), the
`missing_docs` rationale comment in `Cargo.toml`, and warrants an ADR under
`docs/adr/` since it changes a stated structural property. **Benefit:** real
microbenchmarks, and integration tests stop being restricted to driving the
binary through `CARGO_BIN_EXE_cake` (`tests/support/mod.rs:5-7`).

### Option B — binary-driven end-to-end benchmarks only

Keep the crate binary-only; benches shell out to `CARGO_BIN_EXE_cake` the way
`tests/support/mod.rs` does. No architecture change, no ADR.

**Cost:** measures process startup, config resolution, and provider mocking
alongside the code under test. Process spawn overhead (~5-15ms) swamps a
`validate_command_safety` call that should run in microseconds, so the guard —
the highest-value target — becomes unmeasurable. Only viable for whole-run
latency.

### Decision

Take **Option A**. Option B cannot measure four of the five targets. If Option
A is rejected on review, reduce this task to session-replay-at-scale under
Option B and close the rest as won't-do rather than shipping benchmarks that
measure process spawn.

## Scope

1. Settle the lib-target question. If Option A: write the ADR, restructure,
   update `ARCHITECTURE.md` and the `Cargo.toml` lint comment.
2. Add `criterion` to `[dev-dependencies]` and a `[[bench]]` target with
   `harness = false`.
3. Write `benches/bash_safety.rs`: benchmark `validate_command_safety` over a
   representative command corpus — a short allowed command, a long pipeline, a
   blocked `git reset --hard`, a heredoc-bearing command, and a command with
   nested `$(...)` substitutions. Use `Throughput::Bytes(command.len())` so
   results are comparable across input sizes, following
   `nanochat-rs/benches/benchmarks.rs:39`.
4. Write `benches/session_replay.rs`: benchmark `SessionRecord` round-tripping
   at 100 / 1,000 / 10,000 records. This is the scaling-shape benchmark —
   a superlinear curve here is the regression most likely to actually reach a
   user, via `--continue` on a long-running session.
5. Write `benches/edit_diff.rs`: benchmark `generate_unified_diff` on
   small / medium / large files with a single-line edit, since `similar` with
   the `inline` feature is the plausible cost center.
6. Reuse the nanochat-rs Criterion configuration pattern
   (`benches/benchmarks.rs:122-128`): explicit `warm_up_time`,
   `measurement_time`, and `sample_size`, so a `just bench` run finishes fast
   enough to be habitual.
7. Add a `bench` recipe to the `justfile`. **Do not add it to `just ci`** —
   benchmark timings on shared CI runners are too noisy to gate a merge, and a
   flaky perf gate trains people to ignore it.
8. Document in `CONTRIBUTING.md` when to run it: before and after any change to
   `bash_safety`, `edit`, or session serialization.

## Explicitly out of scope

- Any automated performance regression gate. Establishing a committed baseline
  the way `ci/cargo-crap-baseline.json` does for complexity is a plausible
  follow-up, but it needs a stable measurement environment first. File
  separately once there is data on run-to-run variance.
- Optimizing anything. This task measures; it does not tune. If a benchmark
  reveals a real problem, file that as its own task with the numbers attached.
