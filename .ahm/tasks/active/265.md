# Bound Read tool work and enforce its byte cap

## Summary

At commit `6e69b45`, serving a small Read-tool window still scans and allocates every line in the file so it can report an exact total. The output cap is also applied by taking `MAX_OUTPUT_BYTES` Unicode scalar values rather than bytes, so multibyte text can exceed the documented 100 KiB cap by a large factor.

## Evidence

- `src/clients/tools/read.rs:129-150` — `reader.lines().enumerate()` runs to EOF; lines outside the requested window are still allocated as `String` values and counted.
- `src/clients/tools/read.rs:164-170` — output embeds the exact `total_lines`, coupling a small window request to a full-file scan.
- `src/clients/tools/read.rs:173-182` — the byte-sized constant is enforced with `output.chars().take(truncate_at)`, which counts characters rather than encoded bytes.
- `src/clients/tools/read.rs:253-269` — current default-window tests assert exact totals but do not cover bounded work on very large files or multibyte cap enforcement.

## Fix Direction

Bound Read-tool work to what is needed for the requested window and pagination signal, while preserving line numbering and useful remaining-content guidance. Enforce the output limit in bytes at a valid UTF-8 boundary. Keep the Read schema and ordinary output format compatible where possible; do not add indexing, caching, or change unrelated path validation. If exact total-line reporting cannot be retained without a full scan, document the compatibility tradeoff and obtain a decision before changing the visible header.
