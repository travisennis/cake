# Wire cocogitto version bump and changelog into the release path

## Context

The maintainer wants to start cutting releases. Today `release.yml` handles only the back half: a `v*` tag push builds three targets and publishes a GitHub release containing raw binaries. Nothing produces the tag, bumps the version, or generates the changelog. `CHANGELOG.md` contains a single `[unreleased]` section after ~850 commits; no git tags exist; `Cargo.toml` is at 0.1.0. Cocogitto is the sole conventional-commit/changelog owner (`cog.toml` defines `commit_types`; git-cliff config was removed as unused), and the Conventional Commit pre-commit check means history is bump-compatible.

## Work

1. Add a `[bump]` section to `cog.toml` with `pre_bump_hooks` that set the crate version (cargo-edit's `cargo set-version {{version}}` is available via `just setup`) and refresh `Cargo.lock`, and `post_bump_hooks` to push the commit and tag if desired.
2. Decide the changelog anchor for the first release: full 850-commit history or start from a chosen baseline. Cocogitto changelog settings and the first tag placement control this.
3. Cut the first release locally: `cog bump --auto` (or an explicit `--version`), verify `CHANGELOG.md`, `Cargo.toml`, `Cargo.lock`, and the tag, then push the tag to trigger `release.yml`.
4. Optional follow-up in `release.yml`: attach the release's changelog section as the GitHub release body (`cog changelog --at <tag>` into `softprops/action-gh-release` `body_path`), and add artifact checksums. Note: `release.yml` rebuilds binaries rather than promoting CI-validated artifacts — acceptable for now, worth revisiting if releases become consequential.
5. Add a `just release` recipe wrapping the bump flow so the procedure is executable, and document the release procedure in CONTRIBUTING.md.

## Acceptance criteria

- `cog bump` produces a version commit, updated CHANGELOG.md with the release section, and a `v*` tag, with `Cargo.toml`/`Cargo.lock` consistent.
- Pushing the tag produces a GitHub release with the three platform binaries.
- The release procedure is runnable from a documented single entry point (`just release` or documented `cog bump` flow).
- The dependencies-build-ci-release guardrail's warning about treating release workflow changes as ordinary CI edits is respected: workflow changes reviewed by the maintainer.
