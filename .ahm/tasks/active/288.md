# Tolerate empty function-call arguments in Responses API parsing

## Summary

At commit `c0b7faa`, `parse_function_call_output` treats an empty `arguments` string as a malformed function call and errors the entire turn. Some providers send `""` (or omit arguments) for parameterless tool calls — the toolbox argument parser already tolerates this with the comment "some models send none for parameterless tools" and substitutes `{}`. The Responses parser rejecting the same input means a whole run dies on a provider quirk the rest of the codebase deliberately accepts.

## Evidence

- `src/clients/responses.rs:434-445` — `arguments.is_empty()` is grouped with genuinely-missing `id`/`call_id`/`name` as malformed.
- `src/clients/tools/toolbox.rs:209-212` — `parse_arguments` maps empty/whitespace arguments to `{}` with an explanatory comment.

## Fix Direction

Accept empty (or absent) `arguments` for function calls whose other required fields are present, normalizing to `"{}"` (or passing through `""` and letting per-tool parsers handle it — pick one and keep tool-execution semantics unchanged for the built-in tools, which all require fields and will produce their normal parse errors). Keep the malformed error for missing/empty `id`, `call_id`, and `name`.

## Decision

Normalize missing, empty, or whitespace-only `arguments` to `"{}"`, matching
the established toolbox parser behavior. Keep non-empty argument strings
unchanged and retain malformed-call errors for missing identifiers or names.
