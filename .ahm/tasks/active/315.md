# Reclaim leaked per-process secure temp directories

## Summary

At commit `e569256`, every cake process mints a fresh secure temp directory `<tmp>/cake-<uid>-<random>` and nothing ever removes it. On a developer machine that runs cake regularly this accumulates indefinitely: a measured sample showed 626 directories and 125 MB, the oldest 13 days old.

## Problem

The unguessable random suffix that makes the directory safe on a shared `/tmp` (task 267, task 285) also makes it unreusable across runs, so each invocation leaks one directory. Most are empty, because the macOS sandbox probe creates the directory eagerly at startup whether or not anything is ever written into it. The rest hold `bash_output_*.txt` and `bash_binary_*` artifacts from overflowed Bash output.

Nothing here is a correctness or security failure — the permissions and ownership checks still hold. It is unbounded disk and inode growth in the user's temp directory, and on systems where `/tmp` is not periodically reaped it never self-corrects.

## Evidence

- `src/clients/tools/secure_temp_dir.rs:64-82` — `create_secure_temp_dir` builds `<tmp>/cake-<uid>-<random>` per process; the `OnceLock` caches it for the process lifetime and no removal path exists.
- `src/clients/tools/sandbox/macos.rs:48` — the sandbox availability probe calls `secure_temp_dir()` during startup, so the directory is created even for runs that never overflow Bash output.
- Measured locally: 626 directories, 125 MB, oldest 13 days.

## Fix Direction

Decide between two shapes; they trade off differently and the choice should be explicit.

1. **Best-effort cleanup at exit.** Remove the directory on normal shutdown when it is empty, or unconditionally, from the same place that handles graceful shutdown (see ADR 011). Simple, but leaves directories behind on `SIGKILL`, on panic, and on any path that bypasses the shutdown hook — which is exactly the population that accumulates today.
2. **Stable per-uid directory with age-based pruning.** Use one validated `<tmp>/cake-<uid>` root and prune entries older than a threshold on startup. This reclaims directories leaked by prior crashed runs, but the path becomes predictable, so it must keep the full validation from tasks 267 and 285: non-following `symlink_metadata`, ownership check, `0o700` enforcement, and fail-closed behavior when validation fails. Per-run artifacts would live in an unguessable subdirectory beneath it.

A third, cheaper option worth considering alongside either: make the sandbox probe stop forcing directory creation, so runs that never write an artifact never create anything.

Whichever is chosen, do not weaken the ownership or permission guarantees, do not make the artifact path unreadable to the sandboxed agent within its own run, and keep the fail-closed behavior when the secure directory cannot be established. Pruning must never follow a symlink out of the temp root or remove a directory owned by another uid.

## Acceptance Notes

- [ ] Repeated cake invocations do not accumulate one temp directory per run under the chosen strategy.
- [ ] Ownership, `0o700`, non-following symlink validation, and fail-closed establishment behavior are preserved and still tested.
- [ ] If pruning is adopted, tests cover a foreign-uid entry, a symlinked entry, and a concurrent second cake process using the same root.
- [ ] Bash overflow and binary artifacts remain readable by the agent for the duration of the run that produced them.
- [ ] The chosen strategy's residual leak cases (for example `SIGKILL` under option 1) are stated in the task or in `docs/security.md`, not left implicit.
- [ ] `cargo test bash sandbox` and `just ci` pass; the macOS sandbox path is verified on macOS.
