# Prototype View-Anchored EditRange Semantics

## Summary

At commit `fe8dd67`, Cake's literal Edit tool makes the model reproduce exact `old_text` even when Cake just supplied that text through Read. Prototype an additive, disabled-by-default `EditRange` path in which Read records a bounded file view and the model identifies a replacement by `view_id` and line range. The experiment must preserve compare-and-set safety, measure its effect on cheaper models, and leave the existing Edit contract and default tool set unchanged until a later explicit decision.

## Blocker

Blocked on task 306, `Establish a Controlled Model Evaluation Harness`, because the prototype's purpose is to compare correctness, retries, tokens, and turns against literal Edit on identical tasks. This is Effort L and requires an ExecPlan linked from this task before implementation. The ExecPlan must use the evaluation harness for the default/no-default decision and must not assume that lower Edit-call failure alone means better end-to-end task quality.

## Evidence

- `src/clients/tools/edit.rs:23-60` defines the current schema as `{path, edits: [{old_text, new_text}]}`; `old_text` must be unique and reproduced exactly by the model.
- `src/clients/tools/edit.rs:293-346` rejects missing and ambiguous literal matches after scanning the normalized file content.
- `.ahm/tasks/active/234.md:90-129` records a post-JSON-repair corpus of 1,116 Edit calls with an 11.5% failure rate. Of 77 `old_text` no-match failures, 31 followed the model's own earlier edit using a stale view, and 34 of 35 nearby-read cases followed a partial/ranged read.
- `.ahm/tasks/active/297.md:19-35` records the same dominant failure class and notes that the current Read/Edit descriptions cannot make unseen or stale content reliable.
- `.ahm/research/topics/harness-anchored-editing.md:10-20` proposes storing the exact returned Read range and letting the model reference `path`, `view_id`, `start_line`, `end_line`, and `new_text`; Cake validates current content against the remembered view before mutation.
- `.ahm/research/topics/harness-anchored-editing.md:150-194` specifies additive `EditRange` semantics: 1-indexed inclusive ranges, atomic non-overlapping edits, range containment, stale-view rejection, and reverse-order application after validation.
- `ARCHITECTURE.md:33-42` makes tool schemas and filesystem validation compatibility and safety surfaces. `src/clients/tools/`, its descriptions, and snapshots are authoritative.

## Fix Direction

Create an in-memory, per-agent `FileViewStore` shared by Read and an experimental `EditRange` executor. A successful ranged Read should register the exact canonical path, returned line bounds/content, line-ending facts, and an opaque view identifier; `EditRange` must validate the identifier, canonical path, requested bounds, and unchanged current range before calculating byte offsets and applying all requested replacements atomically. Return bounded diff/context output and a precise stale-view error that directs the model to re-read.

Keep the experiment additive and disabled by default through a narrowly scoped feature or experimental switch. Do not change literal Edit, flatten its schema, implement bulk regex transforms, persist views in session JSONL, make views survive resume/compaction, or change the default tool registry in this task. Existing tasks 117, 139, and 234 remain separate; reuse safe edit primitives where sensible but do not absorb their scope.

Files likely in scope are `src/clients/tools/read.rs`, `src/clients/tools/edit.rs` or a new focused `edit_range.rs`, `src/clients/tools/mod.rs`, agent/tool execution context state, focused tests, tool/request snapshots under the experimental configuration, and the evaluation fixtures from task 306. Reuse existing path validation, CRLF/BOM handling, atomic preflight, diff formatting, and per-path scheduling rather than creating parallel safety rules.

If the design requires a new persisted-session record, a default-visible tool contract, a security-boundary relaxation, or a major dependency, STOP and record the design choice through the appropriate ADR/ExecPlan update before proceeding. If the controlled evaluation shows worse correctness or confusing view-selection failures, retain the prototype as non-default evidence or remove it; do not tune the benchmark or hard-code coaching to force a favorable result.

## Acceptance Notes

- [ ] An ExecPlan is created and linked before implementation, with explicit milestones for the view store, experimental tool, safety tests, and controlled evaluation.
- [ ] With the experiment disabled, the default tool registry, request snapshots, CLI behavior, and literal Edit semantics are byte-for-byte/behaviorally unchanged.
- [ ] Successful Read output under the experiment exposes one opaque `view_id` and the store retains only the exact bounded content needed for later validation; storage has a documented bound or eviction policy.
- [ ] `EditRange` supports replacement, deletion, and an unambiguous insertion form; all edits in one call validate before any write and overlapping/out-of-view ranges are rejected.
- [ ] A stale view, wrong path, unknown/evicted view, shifted target range, binary file, invalid UTF-8, and read-only path each fail without modifying the file and with model-actionable text.
- [ ] CRLF, BOM, final-newline, Unicode byte offsets, multiple atomic edits, and unrelated changes outside the target range have focused tests following the existing patterns in `src/clients/tools/edit_tests.rs` and `src/clients/tools/read.rs`.
- [ ] Ephemeral-view behavior across `--continue`/`--resume` is explicit: old view IDs are not silently accepted. No existing session record is rewritten.
- [ ] Task 306 runs identical edit-focused cases with literal Edit and the experimental tool on at least one cheaper configured model when available, reporting end-to-end correctness, Edit failures, recovery turns, output tokens, and wall time. If real-model execution is unavailable, record the blocker and still run deterministic executor tests.
- [ ] The evaluation result and a recommendation (`make default`, `continue experiment`, or `reject`) are recorded without changing the default in this task. A later default change requires its own accepted ADR/task.
- [ ] If a dependency is added, run `just check-deps` and the binary-size audit before proposing default inclusion.
- [ ] Run `just ci` and expect all checks to pass.
