# Drive bash_safety Tests From an External Case Corpus

**Source:** 2026-08-01 comparison of cake against `nanochat-rs`
(`~/Projects/coding-agents/nanochat-rs`), whose `tests/fixture_test.rs:22-25`
declares a `datatest-stable` harness turning every JSON file under a directory
into an independently named test case.

## Problem

`bash_safety` is cake's command guard: 2,124 lines across `checks.rs` (1,119)
and `parse.rs` (1,005), covered by 153 hand-written `#[test]` functions (64 in
`checks.rs`, 89 in `parse.rs`).

The tests themselves are good. `checks.rs:552-600` defines `assert_blocked`,
`assert_allowed`, and `assert_warned` helpers, and cases are grouped by check
with section banners. This task is **not** a correctness complaint.

The problem is the cost of adding a case. `bash_safety` is the module where
cases arrive one at a time and forever — a new destructive `git` invocation, a
quoting trick that slips past `strip_shell_data`, an `env`-prefixed command
form. Each one currently means opening a 1,119-line Rust test module, finding
the right banner section, and either extending an existing `#[test]` (where it
disappears into a list of `assert_blocked` lines and stops being individually
named) or writing a new one.

That friction lands hardest on exactly the contributions most worth having:
someone reporting a bypass they hit, or an agent adding the regression case for
a bypass it just found. Neither should require navigating a Rust test module.

A second, smaller cost: when a case is folded into a multi-assert `#[test]`, a
failure reports the enclosing function name, not the command. The `assert_*`
helpers do interpolate the command into the panic message, which softens this,
but the test *name* is still the wrong granularity.

## Decision

- Move the case data out to a corpus; keep the checking logic in Rust.
- **Do not delete the existing `#[test]` functions wholesale.** Tests that
  assert on message *content*, exercise a single check function via `run_check`
  (`checks.rs:601-605`), or cover parsing primitives with structured returns
  (`split_segments` → `Vec<&str>`, `extract_command_substitutions` →
  `Vec<String>`) do not fit a flat `{command, expect}` shape and must stay.
  Migrate only the `assert_blocked` / `assert_allowed` / `assert_warned` cases,
  which are the repetitive majority and the ones contributors actually add.
- **Do not use `datatest-stable`** despite it being the source of the idea.
  Its per-file granularity requires one file per case, and it registers tests
  from an integration-test harness in `tests/` — which cannot reach
  `validate_command_safety`, a `pub(super)` item in a binary-only crate (see
  the lib-target constraint documented in the benchmarks task). A single
  in-crate test that reads a corpus file gets the same contributor ergonomics
  with none of that.
- Corpus format: **JSONL**, one case per line, in
  `src/clients/tools/bash_safety/corpus/commands.jsonl`. One line per case
  keeps diffs readable and appends conflict-free. Shape:

  ```json
  {"command": "git reset --hard HEAD~3", "expect": "blocked", "note": "destructive history rewrite"}
  {"command": "git status", "expect": "allowed"}
  {"command": "rg -rn pattern .", "expect": "warned", "note": "footgun, not destructive"}
  ```

  `expect` is one of `blocked` / `warned` / `allowed`. `note` is optional and
  exists so a case can carry the reason it was added.
- Load with `include_str!` so the corpus is compiled in and no runtime path
  resolution or working-directory assumption is involved.
- The runner reports **every** failing case before panicking, with the command
  text in the message. A corpus test that stops at the first failure is worse
  than the status quo, since one regression would hide the rest.
- Reject an empty or unparseable corpus loudly — a typo that silently reduces
  the corpus to zero cases must fail, not pass vacuously.

## Scope

1. Add `src/clients/tools/bash_safety/corpus/commands.jsonl`.
2. Add a corpus runner as a `#[cfg(test)]` module under
   `src/clients/tools/bash_safety/`. It parses each line, dispatches on
   `expect`, accumulates mismatches, and panics with the full list. Keep
   `serde_json` (already a dependency) for parsing; do not add a crate.
3. Migrate the `assert_blocked` / `assert_allowed` / `assert_warned` cases from
   `checks.rs` into the corpus. Preserve case-sensitivity coverage — e.g.
   `GIT RESET --HARD` and `Git Reset --Hard` at `checks.rs:60-65` are distinct
   cases and each needs its own line.
4. Delete only the `#[test]` functions fully absorbed by the corpus. Leave
   message-content, `run_check`, and parsing-primitive tests in place.
5. Confirm coverage does not regress: run `just check-coverage`, which enforces
   both the coverage threshold and the `ci/cargo-crap-baseline.json` untested-
   complexity baseline. Regenerate the baseline with `just change-risk-baseline`
   only if the diff is understood and explained, and commit it with the change.
6. Document the corpus in `CONTRIBUTING.md`: adding a `bash_safety` regression
   case means appending one line to `commands.jsonl` and nothing else.

## Follow-ups

`json_repair::repair_json_args` (`src/clients/tools/json_repair.rs:29`) has the
same shape — malformed tool-call arguments observed in the wild, accumulating
one at a time — and would suit an `{input, expected_output}` corpus. It is a
much smaller module, so it is not worth coupling to this task. File separately
once the `bash_safety` corpus has proven the pattern.
