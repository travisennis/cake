# Bound hook output while reading instead of after

## Summary

At commit `e569256`, hook execution reads the child's stdout and stderr to completion into memory and applies `HOOK_OUTPUT_LIMIT` only afterward. A hook that emits gigabytes inside its timeout window grows cake's resident memory without bound. The toolbox path already solves this correctly with `read_streams_bounded`; the hook path should reuse it.

## Problem

`timeout(command.timeout, child.wait_with_output())` collects both pipes in full. The 64 KiB cap is enforced by `capped_text`, which runs on the already-materialized `Vec<u8>`. The timeout bounds elapsed time, not bytes: a hook writing at a few hundred MB/s for a 30-second timeout can allocate tens of gigabytes before cake ever gets to truncate.

Hooks are trusted extensions, so this is a robustness and resource-exhaustion concern rather than a trust-boundary violation — a buggy or noisy hook (a build script accidentally streaming full output) is the realistic trigger.

## Evidence

- `src/hooks.rs:717` — `timeout(command.timeout, child.wait_with_output())` reads both streams to EOF into memory.
- `src/hooks.rs:16` — `HOOK_OUTPUT_LIMIT` is 64 KiB.
- `src/hooks.rs:942-951` — `capped_text` truncates after the fact, once the full output is already resident.
- `src/config/toolbox.rs:398-453` — `read_streams_bounded` is the correct pattern: it stops accumulating stdout past the cap, keeps draining stderr so the child cannot block on a full pipe, and retains only the first `stderr_cap` bytes. Its doc comment already describes it as shared between the describe and execute paths.

## Fix Direction

Switch hook execution to piped stdout/stderr read through `read_streams_bounded`, with `HOOK_OUTPUT_LIMIT` as the cap for both streams, then wait on the child. Keep the existing timeout semantics and the process-group kill guard from tasks 264 and 282 intact — the guard must still defuse only on normal completion, and a hook that stops reading stdin must still not hang cake.

Preserve the model- and session-visible hook output shape: the truncation marker text in `capped_text` is part of what hooks produce into session records, so either keep producing the identical marker or update the hook protocol documentation in `docs/integrations.md` deliberately. Preserve hook decision parsing on the JSON path — a hook whose JSON output exceeds the cap must fail or truncate the same way it does today.

## Acceptance Notes

- [ ] Timeout, process-group termination on timeout, and non-reading-stdin behavior are unchanged and still covered.
