# Serialize a Write that creates a file with a same-turn Edit of that file

## Summary

At commit `c0b7faa`, the tool-call scheduler groups mutating calls by canonical target path so same-file mutations run sequentially (ADR-013). But Edit's `mutating_target` resolves through `validate_path_for_write` → `canonicalize`, which fails for a file that does not exist yet. So the turn "Write new file, then Edit that same new file" produces two independent groups that run concurrently, and the Edit nondeterministically fails with "Failed to access file" depending on whether the Write has landed. Write's own `mutating_target` handles nonexistent paths correctly (two Writes to the same new file are serialized), so the asymmetry looks unintended.

## Evidence

- `src/clients/tools/scheduling.rs:41-50` — `Some(Ok(path))` groups; `Some(Err(_))` and `None` fall through to singleton groups.
- `src/clients/tools/edit.rs:88-102` — Edit's `mutating_target` uses shared `validate_path_for_write` (`mod.rs:790-802`), which requires the path to exist via `canonicalize`.
- `src/clients/tools/write.rs:50-59, 116-174` — Write's `mutating_target` resolves nonexistent suffixes lexically, so it succeeds for new files.
- `src/clients/tools/scheduling.rs:275-299` — the existing test `serializes_second_write_for_same_nonexistent_file` proves the Write side works; there is no Write-then-Edit-new-file test.

## Fix Direction

Make Edit's scheduling target resolution tolerate nonexistent files the same way Write's does (resolve the deepest existing ancestor plus lexical remainder) so Write→Edit on the same new path lands in one group. The Edit executor's own existence check still produces the proper error when the file genuinely never appears. Do not change ADR-013's decision that reads stay concurrent with mutations.
