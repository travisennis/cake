# Prevent dangling function_call items in history from correction turns and pre-hook failures

## Summary

At commit `c0b7faa`, two paths append `FunctionCall` items to conversation history without ever appending matching `FunctionCallOutput` items. The Chat Completions builder then faithfully emits an assistant `tool_calls` message with no following `tool` messages, which OpenAI-compatible providers reject with 400, and the Responses input has the same unmatched-call problem. The result is a confusing provider error (or a poisoned session on resume) instead of the intended failure mode.

Path 1: in output-schema correction mode, tool calls from a misbehaving provider are recorded but deliberately not executed, then the loop re-enters with the dangling calls still in history.

Path 2: if a PreToolUse hook invocation returns an error, `plan_tool_calls` propagates it with `?` after the turn's items (including the function calls) were already streamed and persisted; a later `--resume`/`--continue` of that session replays the dangling calls.

## Evidence

- `src/clients/agent/agent_loop.rs:97` — `extend_turn_items(items)` moves the turn's `FunctionCall` items into history before the correction-mode check.
- `src/clients/agent/agent_loop.rs:113-121` — correction mode records a schema-correction failure and `continue`s without executing the calls or pushing outputs.
- `src/clients/agent/agent_loop.rs:163-166` — a pre-hook error aborts `send()` after items were persisted.
- `src/clients/chat_completions.rs:242-292` — unmatched calls serialize as assistant `tool_calls` with no `tool` messages.

## Fix Direction

For the correction-mode path, append synthetic `FunctionCallOutput` items (e.g. "not executed: correction turn offers no tools") for each unexecuted call before continuing, so the history stays well-formed for both backends. For the pre-hook error path, either record synthetic error outputs before propagating, or handle hook errors per-call as blocked plans instead of failing the whole turn. Preserve session file compatibility: synthetic outputs are ordinary `function_call_output` records.

## Decision

For pre-hook invocation errors, append synthetic error outputs for every
unexecuted call and then propagate the existing error. This repairs persisted
history without changing the current fail-closed hook semantics or turning an
invocation failure into a per-call policy decision.
