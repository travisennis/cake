# Give lint-module-size teeth or remove it from the ci gate; assess the cargo-crap ratchet's value

## Context

Two controls in the `just ci` gate have questionable cost/benefit:

1. `scripts/lint-module-size.py` states "Exit code is always 0; this is an informational lint" yet runs inside the `just ci` gate (justfile lines ~85, ~104). A gate control that cannot fail costs a run and reader attention on every pass while preventing nothing.
2. The cargo-crap coverage/complexity ratchet (`ci/cargo-crap-baseline.json`, checked by `scripts/check-coverage.sh` in `just ci` and the CI Coverage job) has required baseline updates in 21 of 845 commits (~2.5%) — a recurring feeding cost.

## Work

1. For `lint-module-size.py`: either make threshold violations exit non-zero (a real gate) or move the recipe out of `ci` into an on-demand recipe. Pick based on whether a module-size violation has ever been acted on.
2. For cargo-crap: search git history and CI history for cases where the crap regression check failed and blocked a real untested-complexity regression (as opposed to baseline-refresh churn). Record what is found. Keep the ratchet if it has caught regressions or the team values the pressure; otherwise drop it from `just ci`/CI and delete the baseline.

## Acceptance criteria

- No control remains in the `just ci` gate that cannot fail.
- A recorded keep/drop decision for the cargo-crap ratchet with the evidence that supports it.
- justfile, CI workflow, CONTRIBUTING.md, and the dependencies-build-ci-release guardrail stay consistent with the outcome.
