# Add Opt-In LLM-Judge Escalation Tier and Bash reason Argument

**Created:** 2026-07-18
**Source:** Design exploration of an LLM-based alternative to `bash_safety`, synthesized in `.ahm/research/topics/llm-judge-bash-safety.md`.

## Problem

The declarative command policy (task 241 / ADR-015) makes command safety
deterministic and user-owned, but any rule-based system loses by construction
to the long tail: destructive commands behind variables, aliases, `xargs`,
`find -delete`, encodings, or tools no rule enumerates. An LLM can evaluate
what a command *means* and improves for free as models improve — but it is
non-deterministic, costs latency/tokens on the hottest tool, depends on
whatever backend the user configured, and fails in a correlated way under
prompt injection (the judge can be manipulated by the same hostile context
that manipulated the main agent). See the research note for the full
trade-off analysis.

## Direction

Add an **opt-in LLM-judge escalation tier** above the declarative policy, plus
a `reason` argument on the Bash tool. Constraints that make this safe:

- Deterministic policy evaluates first. A policy hard block is final; the
  judge can never overturn it.
- The judge only evaluates commands the policy did not decide (no block, no
  warn — or configurably, also warns).
- Judge verdicts default to **warn** (advisory text prepended to tool
  output). Whether a judge verdict may *block* is a `policy.toml` decision
  the user makes, never a harness default — this keeps the tier consistent
  with the mechanism-over-judgment direction.
- Fail open on judge unavailability/timeout, with a metadata-only telemetry
  event recording the skip. Never make Bash unusable because a judge API is
  down.
- Judge model, timeout, and enablement are user configuration; off by
  default.
- The `reason` argument is untrusted self-report. The judge prompt weighs the
  command over the reason and treats incongruence between them as a signal; a
  benign reason must never launder a hostile command. The `reason` argument
  itself is severable and can ship first (it aids telemetry and session
  analysis even with no judge).
- Judge verdicts flow through the same structured decision / telemetry
  plumbing 241 builds (metadata only: decision, tier, latency; no command or
  reason content in telemetry).

## Prerequisites

- Task 241 complete: structured policy evaluation results, stable rule IDs,
  invocation policy snapshots, and decision telemetry are the plumbing this
  tier plugs into.
- Decide before implementation (likely a small ADR or an ADR-015 amendment):
  judge prompt ownership (embedded vs user-overridable), whether warns also
  escalate, and per-session verdict caching semantics.
- Evidence check: once 241's per-rule fire counts exist, use telemetry to
  estimate how much risky-command traffic escapes deterministic rules. If the
  long tail is negligible in practice, this task may not be worth its cost —
  cancel with evidence rather than building it.

## Acceptance Notes

- [ ] Bash tool accepts an optional `reason` argument; present in transcripts
      and available to session analysis; documented as untrusted.
- [ ] Judge tier is off by default; enabling requires explicit user config
      naming a judge model.
- [ ] Policy hard blocks are provably not overridable by the judge (test).
- [ ] Judge unavailability fails open with a telemetry skip event (test).
- [ ] Judge verdict authority (warn-only vs may-block) is user policy, not a
      compiled default.
- [ ] No command text or reason text in telemetry; metadata-only events.
- [ ] Docs distinguish the three layers: OS sandbox (boundary), declarative
      policy (deterministic user-owned rules), judge (best-effort advisory
      filter).
