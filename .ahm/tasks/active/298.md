# Add an AGENTS.md conformance report to session-metrics

**Source:** Multi-session analysis 2026-07-27 (143 sessions, 2026-07-13 .. 2026-07-27, 396 invocations, 7,504 tool calls).

## Problem

`scripts/session-metrics/` measures cake's *mechanics* well — `tools.py` covers per-tool failure rates and retry recovery, `outcomes.py` covers task success and permission denials, `hooks.py` covers hook decisions. Nothing measures whether agents actually **follow the repository's own operating loop**, and that is where the real losses are. All of the following had to be hand-computed with throwaway scripts for the 2026-07-27 analysis:

  | Signal                                                              | Measured rate                            |
  | ------------------------------------------------------------------- | ---------------------------------------- |
  | `ahm prime` run (AGENTS.md operating loop step 1, "before any work") | 10 of 25 cake code sessions (40%)         |
  | `.md` edited with zero doc check (`panache` / `just docs-check`)     | 24 of 29 cake sessions (83%)              |
  | Hand-rolled `cargo` where a `just` recipe exists                     | `cargo clippy` 131 vs `just ci` 54        |
  | Exact-duplicate Bash commands within a session                       | 405 of 3,782 (10.7%)                      |
  | Code edits with no verification at all                              | 6 of 36 editing sessions (17%)            |

The sharpest single example: session `0f41cdcb` ran the literal string `cargo clippy --all-targets --all-features -- -D warnings` **24 times**. That string is the body of `just clippy-strict`, verbatim. A conformance report would have surfaced this as a one-line finding.

## Direction fit

This is the measurement layer the 2026-07-07 triage named as the correct home for this class of signal — cancelled task 198 was rejected specifically because in-loop coaching heuristics were the wrong layer and "context-window management (task 208) and session-metrics measurement are the right layers". This task adds no runtime behavior to cake at all; it reads persisted evidence after the fact.

It also makes the compliance findings falsifiable over time, which is what "every compensation has an expiration review" (task 244) requires. Any AGENTS.md rule added in response to these findings can be checked against this report later instead of re-litigated from memory.

## Fix direction

Add `scripts/session-metrics/conformance.py` following the existing conventions in that directory: stdlib-only, accepts `--days`, `--sessions-dir`, `--telemetry-dir`, `--model`, `--project`, and is picked up by `report.py`.

Sections to report, per session that mutated files:

1. **Operating-loop steps** — `ahm prime` present; managed work started/completed via `ahm` when task files were touched.
2. **Verification coverage** — code edits (`.rs`/`.toml`) with no `cargo`/`just` invocation; `.md` edits with no doc check.
3. **Recipe drift** — Bash commands whose text equals the body of a `justfile` recipe. Parse the `justfile` directly so the check cannot go stale; this is the mechanically strongest signal in the set.
4. **Commit hygiene** — commits followed in the same session by `git commit --amend` or by a follow-up commit touching only `snapshots/` or task-record paths. This is the signature of the staging problem in task 180.
5. **Repeated commands** — exact-duplicate Bash within a session, with the top offenders named.

Report rates and name the offending sessions, matching how the other scripts present findings. Do not add pass/fail gating — this is a report, not a hook, and several of these rates are legitimately non-zero (doc-only sessions correctly skip `cargo`).

Note that `area:unknown` conformance for non-cake projects (ahm, cake-repl) will appear in the same corpus; `--project` already handles that filtering.
