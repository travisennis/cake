# Record Real Provider Responses as Replayable Wire Fixtures

**Source:** 2026-08-01 comparison of cake against `nanochat-rs`
(`~/Projects/coding-agents/nanochat-rs`), whose `gen-fixtures.sh` regenerates
parity fixtures from the reference implementation, pinned against a documented
tolerance and re-runnable on demand.

## Problem

Every mocked provider response in cake is **hand-written**. `wiremock` appears
in six test files (`src/clients/responses_response_parsing_tests.rs`,
`src/clients/chat_completions_tests.rs`, `src/clients/agent/agent_tests.rs`,
`tests/session_telemetry.rs`, `tests/toolbox.rs`, `tests/resume_repair.rs`),
and in all of them the body is an inline `serde_json::json!({...})` literal —
see `responses_response_parsing_tests.rs:14` and `:29-32`, or
`agent_tests.rs:799`.

Hand-written mocks test cake's parser against **cake's own belief** about the
wire format. They cannot detect the failure mode that actually matters here:
a provider changing its response shape. Cake supports two API surfaces (Chat
Completions and Responses) across many OpenAI-compatible providers, several of
which implement those specs loosely. When a provider adds a field, changes
where reasoning content sits, or alters a tool-call envelope, cake's tests stay
green and the failure surfaces in front of a user.

This is the same class of risk nanochat-rs handles with `gen-fixtures.sh`:
freeze what the real thing actually produced, then test against that rather
than against your own recollection.

The exposure is concentrated in `src/clients/responses.rs`,
`src/clients/chat_completions.rs`, and their `*_types.rs` deserialization
targets, where `ARCHITECTURE.md` places the translation boundary
("Backends translate it at their edges; provider-specific wire shapes must not
become a second conversation model. Request and response snapshots protect
those translations").

## Decision

- Add an **opt-in recording script** that performs real provider calls and
  writes the raw responses to a fixture directory. Replace inline `json!`
  bodies in the parsing tests with those fixtures loaded via `include_str!`.
- **Recording is manual and never runs in CI.** It needs network access, a real
  API key, and costs money. CI replays committed fixtures only. This is a
  hard boundary: no CI job may hit a provider.
- **Scrub before writing.** The script must strip `Authorization`, `x-api-key`,
  `openai-organization`, cookies, and any `set-cookie` from anything captured,
  and must never write request headers to disk. Recorded bodies also carry
  account-correlatable values — request/response `id`s, org-scoped model
  strings, fingerprints — so scrub or placeholder those too. Have someone
  actually read a recorded fixture before the first commit; this is the step
  most likely to leak.
- **Record responses, not requests.** Cake already snapshots outgoing request
  shapes with insta (`src/clients/snapshots/cake__clients__responses__tests__responses_request_*.snap`).
  That direction is covered. The gap is inbound.
- **Fixtures are inputs, not expectations.** Assertions stay in Rust and stay
  shape-based: that a tool call parsed, that reasoning landed in the right
  field, that usage totals populated. Do **not** assert on recorded `id`s,
  timestamps, or token counts — those vary per call and would produce a suite
  that fails on re-record. This is the main way this kind of fixture suite goes
  bad.
- Fixtures are **committed** and reviewed like code. A diff in a re-recorded
  fixture is the signal this whole task exists to produce — it must be visible
  in review, not regenerated silently in a build step.

## Scope

1. Create `tests/fixtures/providers/` with a per-provider, per-API-type layout,
   e.g. `openai/responses/tool_call.json`,
   `openai/chat_completions/reasoning.json`.
2. Write `scripts/record-provider-fixtures.sh`, modeled on the ergonomics of
   `nanochat-rs/gen-fixtures.sh`. It should:
   - read provider config from the existing `settings.toml` mechanism rather
     than inventing new configuration;
   - accept a provider/scenario filter so one scenario can be re-recorded
     without regenerating everything;
   - refuse to run without an explicit `--yes`-style confirmation, since it
     spends money;
   - scrub as described above;
   - pretty-print output with stable key ordering so fixture diffs are readable.
3. Cover these scenarios per API type, chosen because each is a distinct
   parsing path with a real history of provider variance:
   - plain text completion
   - single tool call
   - multiple tool calls in one turn
   - reasoning content present (both the string and content-array forms —
     `responses_response_parsing_tests.rs:116-150` already distinguishes these)
   - a refusal or stop-reason-driven termination
   - a provider error body (4xx/5xx), which is what `src/clients/retry.rs`
     classifies into `RetryReason`
4. Convert `responses_response_parsing_tests.rs` and
   `chat_completions_tests.rs` to load fixtures instead of inline literals.
   Leave `agent_tests.rs`, `tests/toolbox.rs`, `tests/session_telemetry.rs`,
   and `tests/resume_repair.rs` alone — those exercise agent-loop and
   persistence behavior where a hand-written minimal response is the clearer
   test input. Fixtures belong at the parsing boundary only.
5. Add a `record-fixtures` recipe to the `justfile`, marked clearly as manual
   and network-dependent. Do not add it to `just ci` or `just pre-push`.
6. Document in `docs/integrations.md` (which owns provider-facing contracts)
   what the fixtures represent, when to re-record, and that a fixture diff
   means a provider changed its wire format and needs review — not a rubber
   stamp.
7. Record the provider, model, and date each fixture was captured from, in a
   sidecar or a header field. A two-year-old fixture from a retired model
   should be identifiable as stale without guessing.

## Explicitly out of scope

- Streaming/SSE response fixtures. Cake's streaming path deserves the same
  treatment, but chunked recording is a materially different mechanism.
  File separately once the non-streaming pattern is settled.
- Any automated freshness check or scheduled re-record. Decide that after
  there is evidence of how often these actually drift.
