# Do not silently drop sandbox grants for directories that do not exist yet

## Objective

## Blocker

Blocked on #277 — sandbox path customization must be implemented first.

A configured writable sandbox grant naming a directory that does not exist yet
is discarded at startup. Make an absent grant target either be created or
retained, so that granting write access to a directory is sufficient to let a
tool create it.

## Motivation

`valid_settings_dirs` (`src/main.rs:560`) filters `directories` entries with
`p.exists() && p.is_dir()` and drops anything else with a `tracing::warn!`. The
grant then never reaches the writable set at
`src/clients/tools/sandbox/mod.rs:134`.

The consequence is a startup-ordering trap. Granting write access to a state or
cache directory is precisely how a user says "let this tool create and manage
its files here" — but if the tool has not created that directory yet, the grant
is dropped, the sandbox denies the first write, and the tool can never bootstrap
itself. The grant only works once the thing it was supposed to enable has
already happened.

This affects Cake's own dogfooded configuration. `.cake/settings.toml` in this
repository grants `~/.cache/cake` and `~/.local/share/cake`. On a fresh machine,
or after a cache wipe, those directories do not exist and the grants silently
evaporate.

The failure mode is bad out of proportion to the bug. Nothing surfaces at
configuration time; the user sees a denied write from inside a sandboxed run,
far from the config line that caused it. Task 277 keeps warnings file-only, so
the signal stays invisible in the common case.

## Scope

Distinct from task 277. That task adds `~` expansion to `directories` and a
`[sandbox]` section, and moves missing-path warnings to settings-load time. It
does not change the drop-if-absent behavior, so an expanded, correctly written
path for a not-yet-created directory still silently loses its grant.

Sequence this after 277 to avoid conflicting edits to the same loading path.

## Decisions to make

- **Create versus retain.** Either create absent `writable` targets at
  settings-load time, or pass them through to the sandbox unfiltered and let the
  OS layer handle a nonexistent path. Creating directories as a side effect of
  reading configuration is a real cost worth weighing against the trap it
  removes.
- **Whether `read_only` grants behave the same.** Creating a directory to grant
  read-only access to it makes little sense; the argument for `writable` does
  not transfer.
- **Whether the existence filter has a remaining purpose.** It appears to exist
  to catch typos. Typo detection and bootstrap support are in tension, and the
  warning may be the better place for the former.

## Verification

- A `writable` grant for a directory that does not exist lets a sandboxed
  command create and write it in that same run.
- A fresh machine with no `~/.cache/cake` honors this repository's own
  `.cake/settings.toml` grants without a preparatory step.
- Whatever diagnostic is chosen for a genuinely mistaken path remains present
  and is not weakened to enable the bootstrap case.

## Risks

- Creating directories from configuration loading is a side effect in a code
  path that currently only reads, and a typo would silently create a stray
  directory rather than warning about a missing one.
- Behavior under `--sandbox read-only`, which demotes writable grants, needs to
  stay coherent with whichever option is chosen.
