# Clarify Commit/Task-Complete Ordering in Workflow Guidance

**Created:** 2026-05-24
**Source:** Evaluation of session `98433c0e-2228-4d40-9e88-234141f16fc1`

## Problem

The AGENTS.md task queue rules state:

> "When a task includes committing and task-status updates, commit the
> intended code/task changes together unless the user asks for separate
> commits."

This guidance says to commit everything together, but does not specify the
ordering of `ahm task complete <id>` relative to the final `git commit`.
Since `ahm task complete` modifies task files (moves them, regenerates
indexes), the timing matters:

- **Commit first, then task-complete**: Leaves the task-file changes
  uncommitted, creating a second commit and violating "commit together."
- **Task-complete first, then commit**: Ensures all changes (code + task
  files) are in one commit, but the agent must remember to stage the moved
  task files alongside the source changes.

In session `98433c0e-2228-4d40-9e88-234141f16fc1`, the agent:

1. Committed source code changes only (`cbce92a`)
2. Ran `ahm task complete 177`, which modified task files
3. Committed the task-file changes separately (`8f3a40e`)
4. Realized this violated the "commit together" rule
5. Ran `git reset --soft HEAD~2` to undo both commits
6. Staged both source and task files together
7. Made a single combined commit (`7eec0c4`)

This consumed ~3 extra reasoning turns and ~6 git operations that would not
have been needed with clearer ordering guidance.

## Recommendation

Update the AGENTS.md task queue rules to clarify the ordering:

> **Workflow**: When committing and marking a task complete:
> 1. First run `ahm task complete <id>` (or `ahm task cancel <id>`).
>    This moves the task file and regenerates indexes.
> 2. Then stage all changed files — source code, moved task files,
>    regenerated indexes — together with `git add`.
> 3. Finally make a single commit with all changes.

This ensures the agent always ends with one commit containing everything
that changed, without needing to backtrack.

## What the evidence adds beyond the original body

The original task framed this as an *ordering* ambiguity between `ahm task complete` and `git commit`. The sessions show it is that, plus a second independent cause the original body did not capture:

**Generated artifacts land after the status check.** Snapshots are written by verification (`just snapshots` / `cargo insta`), and task files and indexes are written by `ahm task complete`. An agent that builds an explicit `git add` path list from a `git status` taken before those steps will always miss them. `54e43d0b` missed snapshots without any `ahm` involvement at all — so this is not purely an ahm-coupling issue, which answers the cancellation note that "cake itself does not require ahm."

Note `git add -A` does not solve it either: `7cf75989` used `-A` and still needed three amends, because the task-record writes happened after the commit. Ordering is the load-bearing part.

## Existing partial coverage

AGENTS.md already carries "Before broad edits and before handoff, inspect `git status --short`" and CONTRIBUTING.md:65 already carries "complete managed work before any commit containing its implementation." The second rule is the one being violated, and it lives in CONTRIBUTING.md — which the AGENTS.md workflow routing sends agents to only for dependency/build/release work, not for the code routes where these commits happen. That placement, rather than the absence of a rule, may be the actual defect; a fix could be as small as surfacing the existing rule in the AGENTS.md Repository rules section rather than writing new guidance.

## Suggested scope on reopen

Smaller than the original recommendation. Consider:

1. Move or mirror the existing CONTRIBUTING.md:65 rule into AGENTS.md "Repository rules", where the code routes will actually see it.
2. Add that `git status --short` must be re-run *immediately before* `git add`, because verification and task completion write files.

Both are one line. If even that is judged too much guidance, the alternative disposition is mechanical: task 298 (session-metrics conformance report) includes a commit-hygiene section that detects this exact signature — a commit followed by an amend or by a follow-up commit touching only `snapshots/` or task-record paths. That would let the problem be measured rather than instructed, which fits the current direction better. Decide between the prose fix and the measurement-only fix before implementing; do not do both.
