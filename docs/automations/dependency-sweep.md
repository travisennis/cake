# Dependency sweep

This document is the dependency-maintenance procedure for Cake. It is a manual, review-only process until [#231](https://github.com/travisennis/cake/issues/231) decides how Cake runs as a scheduled worker. The process may prepare pull requests or issues, but it never merges or automerges them.

## Ownership and inventory

The report reads the files that already own their values. It does not create a second version manifest. Every row has one owner and one update path.

  | Surface                         | Owner                     | Repository authority                                                                  | Authoritative upstream source                                                                                                   | Update path                                                                       |
  | ------------------------------- | ------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
  | Cargo dependency requirements   | Dependabot                | `Cargo.toml`                                                                          | The dependency's upstream repository and release history                                                                        | Review the Dependabot pull request                                                |
  | Resolved Cargo packages         | Dependabot                | `Cargo.lock`, generated by Cargo                                                      | The exact crate source and its upstream compare                                                                                 | Review and regenerate through Dependabot; never hand-edit                         |
  | GitHub Actions references       | Dependabot                | `.github/workflows/*.yml` `uses:` entries                                             | The action repository's exact ref and source diff                                                                               | Review the Dependabot pull request                                                |
  | Project Rust toolchain          | Dependency sweep          | `rust-toolchain.toml`                                                                 | The official [Rust stable channel manifest](https://static.rust-lang.org/dist/channel-rust-stable.toml) and Rust release source | Update the authority and synchronized pins together                               |
  | Synchronized Rust workflow pins | Dependency sweep          | `toolchain:` values in `.github/workflows/ci.yml`, `release.yml`, and `scheduled.yml` | `rust-toolchain.toml` is the authority                                                                                          | `scripts/check-rust-toolchain.sh` identifies drift                                |
  | Local mise tools                | Dependency sweep          | `.mise.toml`                                                                          | Each tool's official release source                                                                                             | Update the exact mise pin; its Rust value must match `rust-toolchain.toml`        |
  | Local Cargo-installed tools     | Dependency sweep          | `justfile` `setup` recipe                                                             | Each tool's official release source                                                                                             | Update the exact `cargo install` pin with `--locked`                              |
  | Workflow-installed tools        | Dependency sweep          | `cargo install` and `tool:` inputs in workflow files                                  | Each tool's official release source                                                                                             | Update the exact workflow input and the matching local pin when one exists        |
  | MSRV compatibility claim        | Human decision and review | The `msrv` job in `.github/workflows/scheduled.yml`                                   | The decision in [#128](https://github.com/travisennis/cake/issues/128)                                                          | Do not change during a dependency sweep                                           |
  | Cargo udeps nightly             | Human decision and review | The `udeps` job in `.github/workflows/scheduled.yml`                                  | `cargo-udeps` compatibility documentation and the official nightly channel                                                      | Keep the deliberate nightly exception; review compatibility when the tool changes |
  | Cake package release version    | Human decision and review | `[package].version` in `Cargo.toml`                                                   | Cake's release history                                                                                                          | Outside this dependency sweep; use the release process                            |

The report also lists action refs and every extracted tool input. This makes a new surface visible before an updater edits it. Rust workflow pins and the `.mise.toml` Rust value are restatements, not new authorities. The check script and the report must show drift instead of allowing a second value to become authoritative.

The following are version-like project metadata, not dependency surfaces: the Cargo edition, workflow names, release workflow input named `version`, and generated lockfile format. Review them only when their owning workflow or release decision changes.

## Deterministic report

Run the report from the repository root:

```
python3 scripts/dependency-sweep.py
```

The command is read-only. It prints JSON to standard output and returns one of these stable exit codes. It requires Python 3.11 or newer because it parses TOML with the standard-library `tomllib` module:

  | Status            | Exit code | Meaning                                                                                                                       |
  | ----------------- | --------: | ----------------------------------------------------------------------------------------------------------------------------- |
  | `no-work`         |         0 | The inventory is valid and the supplied release data identifies no update.                                                    |
  | `actionable`      |        10 | All findings are understood, passed the cooldown, and may be reviewed for one bounded change.                                 |
  | `review-required` |        20 | A source is missing or ambiguous, a pin drifted, a release is too new, or a human decision is required. Do not guess or edit. |

The report has `schema_version: 1`, `repository`, `status`, `exit_code`, `inventory`, `findings`, `rust_release`, and `summary` fields. Each inventory item contains `id`, `domain`, `owner`, `authority`, `path`, `name`, and `current`. Findings contain a stable `code`, `classification`, `domain`, and `reason`; update findings also contain the old and candidate values and their release age. A report with missing or malformed release data remains JSON and returns `review-required`.

The local inventory is deterministic. Rust release comparison is deterministic when the official channel is saved as an input. The report never silently contacts a changing service. Supply the channel and the UTC date explicitly for a complete run:

```
curl --fail --silent --show-error https://static.rust-lang.org/dist/channel-rust-stable.toml > /tmp/cake-rust-channel.toml
just dependency-sweep --rust-channel /tmp/cake-rust-channel.toml --as-of "$(date -u +%F)" > /tmp/cake-dependency-report.json
```

`just dependency-sweep` is only a convenience wrapper around the Python command. Its report uses the same schema and exit codes. A command that returns 10 or 20 is an expected report result, not a shell error to hide with `|| true`.

## Release and cooldown rules

The report reads the top-level `date` and `[pkg.rust].version` from the official channel manifest. A new stable release is actionable only after seven full calendar days. The release date must not be later than the explicit `--as-of` date. A missing, malformed, older-than-current, or otherwise ambiguous release is `review-required`.

A confirmed security update may bypass the cooldown only when the maintainer records evidence and supplies it as a reason, for example:

```
just dependency-sweep --rust-channel /tmp/cake-rust-channel.toml --as-of "$(date -u +%F)" --security-reason "RustSec advisory and upstream fix link"
```

The reason is not proof by itself. The review record must link the advisory and the upstream source diff. Security work stays separate from ordinary updates. Major-version changes, MSRV changes, API migrations, security-boundary changes, and updates with a large or unavailable upstream diff are `review-required` and need individual human review.

The repository pin was Rust `1.97.1`. On 2026-08-27, the official channel dated 2026-08-20 reported Rust `1.98.0`, so the complete report identified `1.97.1` to `1.98.0` as actionable with age `7`. The report did not apply that update by itself.

## Manual procedure

Start from a clean checkout of the default branch. These commands are run from the repository root and use no unrecorded local state:

```
git status --short
git fetch origin
git switch master
git pull --ff-only
test -z "$(git status --porcelain)"
curl --fail --silent --show-error https://static.rust-lang.org/dist/channel-rust-stable.toml > /tmp/cake-rust-channel.toml
set +e
just dependency-sweep --rust-channel /tmp/cake-rust-channel.toml --as-of "$(date -u +%F)" > /tmp/cake-dependency-report.json
report_exit=$?
set -e
```

Read the JSON report before doing anything else. Then run `just check-deps`. An advisory failure is a security finding: do not bundle it with ordinary maintenance. Record the advisory output, follow the security-update path below, and create or update the tracked issue path for the failing scheduled check.

When the status is `no-work`, stop. Keep the report as the run record if a maintainer needs evidence. When the status is `review-required`, do not update a pin. Inspect the named source, resolve the decision through a maintainer or [#128](https://github.com/travisennis/cake/issues/128), or create a GitHub issue with the report attached. When the status is `actionable`, review the upstream sources described below and then let Cake prepare only the understood work.

For a Cake-assisted run, create this prompt and invoke Cake from the clean checkout:

```
cat > /tmp/cake-dependency-prompt.txt <<'PROMPT'
You are Cake's dependency-maintenance role. Read docs/automations/dependency-sweep.md, docs/dependencies.md, and /tmp/cake-dependency-report.json before taking action. The report is authoritative for this run's discovered surfaces and status. If its status is no-work, stop. If its status is review-required, do not edit; summarize the missing evidence or decision and prepare a GitHub issue using the normal issue workflow. If its status is actionable, review the exact upstream source diff for each finding before editing. Preserve Dependabot ownership of Cargo and GitHub Actions. Keep changes within the documented domain and count bounds, run the required checks, prepare a reviewable pull request, and never merge or automerge. Every automation-authored issue or pull request comment must start with: Cake automation note:
PROMPT
cake --sandbox workspace-write - < /tmp/cake-dependency-prompt.txt
```

The prompt tells Cake to read `docs/automations/dependency-sweep.md`, `docs/dependencies.md`, and `/tmp/cake-dependency-report.json` before editing. It also preserves the review rules without creating a second policy document. The prompt is a pointer to this procedure, not a second copy of it.

## Upstream review and change bounds

For every proposed update, record the ecosystem, old value, candidate value, release date, and whether it is direct or transitive. Read the exact upstream source compare, not only a release-note summary. For crates, inspect new dependencies, `build.rs` changes, new unsafe code, and process or network behavior. For actions, inspect source, generated `dist` artifacts, downloaded executables, permissions, post-action behavior, and cache or `PATH` handling. If the source diff is unavailable, too large to review, or generated without reviewable source, stop for human review.

Group changes by logical domain. One run may prepare at most one pull request for each of these domains: Rust and its synchronized pins; local and CI developer tools; or another explicitly approved tooling domain. Do not mix Cargo or GitHub Actions Dependabot work into a sweep pull request. Keep a pull request to one domain and at most three related safe pin changes. Put a fourth change in the next run. Keep security updates, major-version changes, and MSRV changes in separate individually reviewed pull requests.

For a Rust toolchain update, change `rust-toolchain.toml` first, update its `.mise.toml` restatement and all non-MSRV `toolchain:` values, then run `just rust-version-check`. Do not change the `msrv` job or the deliberate `nightly` udeps selector. For a local or workflow tool update, retain an exact version and `--locked` for Cargo installs. Never hand-edit `Cargo.lock`.

## Pull requests and issues

Known safe work produces a normal reviewable pull request. The body must include the report, exact upstream compare links, the reason the cooldown passed or the security evidence, the files changed, and the checks run. Use a conventional title, the required `type:*` and `area:*` labels from `.github/labels.yml`, and `Closes #<number>` when the work belongs to a managed issue. Do not merge or automerge the pull request.

Ambiguous or high-risk work produces an issue or remains stopped for manual review. Use the normal GitHub issue workflow and include the report, failed or missing evidence, affected domain, and a concrete next decision. Automation-authored issue and pull request comments must start with the exact prefix `Cake automation note:`. Treat that prefix as automation state, not as maintainer guidance. Human feedback remains an ordinary issue or pull request comment without that prefix.

## Existing scheduled checks

`.github/workflows/scheduled.yml` remains ordinary non-mutating CI. It runs weekly and on manual dispatch:

- `deny` checks advisories and gates its job.
- `outdated` is informational and writes its report to the workflow log; it does not create a pull request. The manual sweep reviews that signal.
- `udeps` checks unused dependencies with its deliberate nightly compatibility exception.
- `msrv` checks the human-owned MSRV claim.
- `docs` checks documentation warnings.

A failed scheduled job follows the tracked issue path in [#236](https://github.com/travisennis/cake/issues/236). The scheduled workflow does not run Cake, create branches, or publish dependency changes. The future scheduler in #231 may call this procedure, but it must not change these dependency-specific rules.

## Verification

For a report-only change, run:

```
just dependency-sweep-check
```

After saving the official channel, verify the live demonstration:

```
just dependency-sweep --rust-channel /tmp/cake-rust-channel.toml --as-of "$(date -u +%F)"
```

For a pull request that changes Rust, configuration, CI, fixtures, or dependency surfaces, run:

```
just check
just check-deps
```

Use `just check-full` when the change needs complete local validation, including coverage, all CI fixtures, documentation, and a release build.

`just check` is the fast local gate. If a check cannot run, record the exact reason and the narrower checks that did run. GitHub CI remains authoritative for platform tests and coverage/change risk. The report and fixture suite require no provider credentials or network access; only the live Rust channel acquisition requires network access. The `changes` job in `.github/workflows/ci.yml` runs the fixture suite, and maintainers can run it locally with `just check-full`.
