# Dependency and supply chain posture

This document defines Cake's dependency intent: what earns a place in the dependency graph, where each version is pinned, and what review an update requires. It is the authority for dependency posture. Concrete pins live in the files named below, and the command catalog lives in [CONTRIBUTING.md](../CONTRIBUTING.md).

Cake ships a binary that executes model-generated commands on a user's machine. Every dependency and every developer tool is code that runs with the user's authority or the CI job's authority, so the dependency graph is part of the trust boundary described in [Security and trust boundaries](security.md).

## Principles

- Prefer the standard library and repo-local helpers when the behavior is small, stable, and easy to test.
- Add a dependency only when it removes more risk or complexity than it introduces. A direct dependency is a standing commitment to track its releases, advisories, and breaking changes.
- Pin developer and CI tooling to exact versions. Tooling determines what the gates actually check, so a floating tool version means the gate is not reproducible.
- Do not use mutable selectors such as `latest`, `stable`, branch names, or floating tags for durable tooling inputs. Cake pins an exact Rust version rather than tracking a channel, because the strict Clippy configuration in `Cargo.toml` makes a compiler upgrade a behavior change to the lint gate.
- Give every version exactly one owning file. A version duplicated across files without a check drifts.
- Apply a one-week cooldown before adopting a newly published toolchain or tool release. Security updates are exempt.
- Keep lockfiles generated by their package managers. Do not hand-edit `Cargo.lock`.

## Pin ownership

Each version-bearing input belongs to one surface, and the owning surface determines where the pin lives.

  | Input                            | Owning file               | Enforcement                         |
  | -------------------------------- | ------------------------- | ----------------------------------- |
  | Crate compatibility requirements | `Cargo.toml`              | `cargo deny check advisories`       |
  | Concrete crate selections        | `Cargo.lock`, committed   | `just check` builds against it      |
  | Rust toolchain version           | `rust-toolchain.toml`     | `scripts/check-rust-toolchain.sh`   |
  | Local toolchain bootstrap        | `.mise.toml`              | none; see [Toolchains](#toolchains) |
  | Cargo-installed developer tools  | `justfile` `setup` recipe | none                                |
  | CI tool versions                 | `.github/workflows/`      | none                                |
  | GitHub Actions versions          | `.github/workflows/`      | Dependabot                          |
  | License and advisory policy      | `deny.toml`               | `just check-deps`                   |

`Cargo.lock` is committed because Cake is a binary crate: the lockfile is the record of what a released binary was built from, not an over-constraint on downstream users.

## Toolchains

`rust-toolchain.toml` is the source of truth for the Rust version. `scripts/check-rust-toolchain.sh`, which runs as part of `just check`, verifies that every `toolchain:` pin in `ci.yml`, `release.yml`, and `scheduled.yml` matches it, and rejects both floating `toolchain: stable` inputs and `dtolnay/rust-toolchain@stable` steps that omit an explicit version. Changing the Rust version means changing `rust-toolchain.toml` and letting that check identify the workflow pins that must follow.

The MSRV job in `.github/workflows/scheduled.yml` is the one deliberate exception, and the check script special-cases it by job name. MSRV is a compatibility claim about the oldest compiler Cake builds on; it moves independently of the toolchain the project develops and releases against, and it should move only as a deliberate decision.

`.mise.toml` bootstraps a local development environment. It is a convenience for contributors, not an authority: when it names a Rust version, that version restates `rust-toolchain.toml` and must match it.

## Rust dependencies

Direct dependencies are the enforceable policy boundary. Understand a transitive set through its direct roots rather than allowlisting individual transitive packages, and treat a direct dependency that pulls in a large or unfamiliar subtree as a cost of that dependency rather than a separate problem.

`deny.toml` records the license allowlist, banned crates, and advisory configuration. `just check-deps` runs `cargo deny check advisories`, and the weekly scheduled workflow runs the same check plus `cargo outdated` and `cargo udeps`.

Known-vulnerability scanning complements dependency judgment but does not replace it. An advisory database reports what is already known about a package; it says nothing about whether the package should be a dependency. A crate with no advisories can still be unmaintained, overbroad, or a poor fit.

Platform-specific dependencies belong behind a target gate, as `landlock` is today. A dependency needed on one platform should not enter the graph on the others.

## Developer and CI tooling

The `setup` recipe in the `justfile` and the tool installations in `.github/workflows/` describe the same tools for two audiences, so they must agree. A contributor whose local tool version differs from CI's gets gate results that CI will not reproduce.

Pin these tools to exact versions with `--locked`. Tools that gate the build --- the formatter, the linter, the coverage and change-risk tooling, the documentation linter --- change their own output across releases, so an unpinned upgrade can turn a green branch red with no source change, or hide a finding the pinned version reported.

## Reviewing a dependency update

Dependabot's pull request shows what changed in this repository. That is not enough to classify an update as safe, because the repository-side diff of a version bump is a line in a manifest. The upstream change is the thing being reviewed.

Before merging a dependency update:

- Identify the ecosystem, the old and new versions or pinned commits, and whether the update is direct or transitive.
- Open the authoritative upstream compare for those exact refs. Read the code diff, not only the release notes.
- For GitHub Actions, pay attention to install and bootstrap behavior, generated `dist` artifacts, transitive executable downloads, workflow permission requirements, post-action steps, and cache or `PATH` handling. An action runs with the job's token.
- For crates, pay attention to new transitive dependencies, `build.rs` additions or changes, new `unsafe` blocks, and process or network behavior that the crate did not previously have.
- Confirm that generated artifacts correspond to their source when a dependency ships generated code.
- Apply the cooldown when the update adopts a newly published release.

If the upstream diff is unavailable, too large to review, or generated without reviewable source, do not merge it on the strength of a green CI run. CI shows that Cake's tests pass against the new version; it does not show what the new version does.

Merge mechanically safe updates. Escalate an update that changes behavior, migrates an API, alters a security boundary, or moves a major version, and keep it separate from unrelated work.

## Enforcement

`just check` runs the fast local gate. `just check-full` adds coverage/change-risk, the CI fixture suites, dependency checks, documentation, and a release build. The scheduled workflow runs advisories, outdated dependencies, unused dependencies, and MSRV weekly. Dependabot opens weekly Cargo and GitHub Actions updates. The manual review procedure for the remaining version surfaces is [Dependency sweep](automations/dependency-sweep.md).

These mechanisms enforce parts of this posture, not all of it. Where a rule here has no check, it is a rule a reviewer applies.
